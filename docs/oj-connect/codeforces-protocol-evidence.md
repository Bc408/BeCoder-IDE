### Stage 缺陷复核与 C++23 回归

2026-11-18，负责人反馈 2121/H 停在“回执尚未确认”。只读核对官网既有记录 **399056530** 已为 Accepted，回读源码与本地文件精确一致（只规范化换行），因此没有重交该题。根因是表单 `GNU G++23 14.2 (64 bit, msys2)` 对应列表 `C++23 (GCC 14-64, msys2)`，旧匹配规则不接受列表中的工具链后缀，过滤了正确记录。修复保持 C++ 版本、GCC 主版本与位数匹配，并在列表带工具链后缀时核对该后缀；没有加入自动重发或另一条查询路径。

题面同时复用已有洛谷来源的时间／内存格式函数，2121/H 显示 `2.00s`、`512.00MiB`；仅移除与原题索引一致的标题前缀，保留题目标识。自动渲染检查覆盖窄宽度与常用分栏宽度，并人工查看生成截图；最终 stage 仍交由负责人验收。

第四次表单读取 2882 ms、并行本人列表 2765 ms，准备合计 2884 ms；从协议计时入口到源码核对 4825 ms。外层开始到该入口还存在 1305 ms 首次临时模块加载边界，未细分归因，故完整外层开始到确认约 6130 ms。终态观察包含官网排队／判题和探针约两秒读取间隔。这不是产品按键到首绘、p95 或长期可靠率统计。

### 2026-11-19 双表回归与构建复核

本机旧 stage 的 `resources/app/out/main.js` 仍要求本人提交页恰好只有一张状态表；当前源码已接受官网分别呈现练习与原比赛历史的双表。旧构建不能作为当前源码修复的运行证据。

在双表解析基础上，隔离用例进一步复现了分页确认缺陷：一张表的旧记录会提前终止另一张表的扫描，既可能漏掉下一页唯一的新回执，也可能将多个同源码候选误判为唯一。修复保留各表的降序记录边界，只有不存在下一页，或每张表都已为空／到达提交前边界时才停止；仍保留五页和十六候选的上限、单次源码发送及唯一官方源码匹配要求。

新增两个用例先观察到错误结果，再以修复后的 27 项协议／传输／Session 测试验证通过；另有用例确认各表均到达旧边界后无需继续读取历史页。含 bridge 的 40 项测试与隔离 Electron host 回归也已通过。本轮没有实交，不将这些结果等同于新 stage 的真实网站闭环或负责人验收。

## 表单与实际请求

- 同一登录 Session 直接 GET `/contest/4/submit?problemIndex=A` 可取得当前表单、账号与编译器选项；无需导航该网页或执行其初始化脚本。
- 源码字段为 `source`；hidden action 为 `submitSolutionFormSubmitted`。题目标识、`csrf_token`、`ftaa`、`bfaa`、`programTypeId`、`tabSize` 与空 `sourceFile` 等按当次官方表单处理。
- 原始 ftaa／bfaa input 为空，服务器 inline 脚本提供字面量。Acorn 只读提取值与官方空页初始化对照一致，不执行远程代码。
- 已核对官网初始化的动作查询参数与基于当前 cookie 的 `_tta` 计算；均留在宿主内存，研究报告不公开值。
- 无文件上传时，官网将 multipart 改为 URL encoded；实交按 `application/x-www-form-urlencoded` 发送。
- `name=action` 的 input 会遮蔽实际浏览器的 `form.action`；JSDOM 未暴露同样现象，必须读取 action 属性并校验官方目标，不能凭开发解析器行为推断 Chromium。
- 未发现固定提交前秒级等待；官方 submitOnce 的约十秒禁用在提交处理之后。第四次冷会话成功进一步排除该样本依赖此前提交页运行的假设。

冷会话只证明该样本不需要提交页预初始化。正常登录和官网验证仍须完成，没有证明免认证或所有网站状态均可直接发送。

## 手动重定向的运行时差异

第一轮 `Session.fetch(..., redirect: 'manual')` 抛出 `Redirect was cancelled`，但随后的只读核对找到了本次 AC，因此没有重发。

在本地回环服务构造 POST→303→GET 对照：Session.fetch manual 同样抛取消错误；同 Session 的 `net.request` manual 可以取得 redirect 事件的状态、方法、目标并停止；Session.fetch follow 得到最终 200。这是 Electron 43.7.3 运行时行为，不是 CF 拒绝的证据。

后三轮使用显式 Session、`useSessionCookies: true`、`redirect: 'manual'` 的 `net.request`。真实回执均为 302，重定向方法 GET，同源 `/contest/4/my`；捕获后停止自动跟随，再明确读取该列表。不依靠错误处理重新 POST，不自动跟随未知目标或 307／308。

Electron 官方 ClientRequest 语义与本地 `node_modules/electron/electron.d.ts` 是实现参考。这里没有复制洛谷的 Node HTTPS 传输，也没有假定两类客户端的手动重定向相同。

## 记录读取与数据陷阱

官网本人列表、problemset 本人状态列表、个人提交列表及公开 contest.status API 均曾读取到精确新 ID。生产候选优先遵循官方提交回执所指向的本场本人列表，不为有限速度样本增加多路径竞速或备用查询。

官网列表通过 POST `/data/submitSource` 读取精确提交，参数为 `submissionId`、`csrf_token`，配合同源请求头。既有本人 AC／WA／CE 和新记录评测中／终态均已读到：源码、状态、编译输出及部分测试信息。本接口是站点内部接口，不是官方稳定提交 API。

- `waiting`、`compilationError` 为字符串 `true`／`false`，不能按 truthiness 判断。
- verdict 与 CE 的 submissionProtocol 可能包含 HTML；提取文本或净化，不能直接注入界面。
- `testCount` 不是可靠全量测试集总数，CE 也可返回 1；结合实际 `accepted#N`／`verdict#N` 等字段，不制造剩余测试点。
- 源码字符数与 UTF-8 字节数不等。原始测试内存为字节，必须核对单位，不能冒充 MiB。
- 没有真实分数／总数时省略；记录页返回的等待期资源零值不作为最终资源展示。
- 第二轮实际观测 Running on test 1→Running on test 2→Accepted；第四轮观测 In queue→Running on test 1→Running on test 18→Accepted，源码回读持续匹配。

本人详情页直接 GET 多次为 Cloudflare 403，不代表已退出或无权限。`/enter` 只读重定向试验也曾读到 403，未完成预期重定向，不能当作成功传输对照。

登录 Session 对 `api/user.status?includeSources=true` 返回 400，网页登录不自动获得该 API 的源码权限；不因此引入 API 密钥。公开 API 可以提供部分记录字段，但本轮不增加第二套结果跟踪。

## 复用结论与未覆盖项

已有 CPH CF parser 在公开 problemset／contest 题面样本中可提取正文／样例，应复用现有能力。第三方插件的页面填码点击只作为生态经验，不作为本项目直接请求成功的依据，不整体迁入框架或未知许可代码。

可收敛为：正常登录的原生 Session→按需读取官方表单与本人边界→一次请求→唯一新 ID 与源码核对→既有共同结果页和本地跟踪。无需由当前证据引入隐藏页、预热、指纹服务、自动重交或通用调度框架。

未验证长期可靠率、过期／切换账号、首次空本人列表、更多题目、所有状态、C 编译器和各类异常。Gym、进行中比赛、虚拟参赛、私有／团队入口与镜像域名不在已选首期范围。比赛结束／普通练习权限、元信息单位和稳定生产解析方式在实施时逐项核准，不因 4A 四次成功推定全部可用。
