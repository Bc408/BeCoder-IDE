# 用户主动生成万能头 gch 缓存

日期：2026-10-19
状态：已实施，源检查、独立实例运行验证、最终应用包及 Setup 直接验证完成；项目所有者于 2026-10-19 确认本次修改完成验收，并授权本地提交及推送至对应分支。

## 1. 目的、现状与权限

BeCoder 是开箱可用的 Windows C/C++ 竞赛环境。gch 是可丢弃的编译加速缓存，不再是必需的安装资产；没有缓存仍须正常编译、运行和测试。

设计起点的只读核对基线为 `84ee903e`，核对时工作区干净。该基线构建按默认 C++20 参数生成相邻 `stdc++.h.gch`，构建清单、包验证和启动健康检查要求其存在；本次实现已移除这些要求。Runner 强制包含 `bits/stdc++.h`、`bits/debugger.h`，CPH 和 Notebook 通过 Runner API 复用编译策略。Windows Runner 当前只读取用户级编译配置。

最初授权为方案收敛和实现准备；随后项目所有者明确授权实现、自行验证与迭代，并交付最终 Setup。未授权提交、推送或发布。旧瘦身调研中的“保留发行 PCH”是历史结论，由本次项目所有者的新决定覆盖，不改写历史证据。

## 2. 已确认决策

- 安装包不再携带或在构建时生成 gch；同步更新安装资产清单和验证规则。
- gch 不参与工具链健康判断；编译器、运行库和原始头文件仍保持必要检查。
- 工具链损坏通知保留获取 Setup，移除“打开诊断”；移除专用工具链诊断页、命令、注册、本地化及针对该页的包要求。
- 不移除独立 GCC 编辑器诊断扩展，也不削弱正常工具链检查。
- 在左下角齿轮菜单加入“生成 gch 缓存”，无额外设置页。
- 只生成 `bits/stdc++.h` 对应的 `stdc++.h.gch`，放在原万能头旁边。没有独立 debugger.h 缓存、项目头缓存、C 缓存或多配置缓存库。
- 每次主动生成清空当前安装拥有的所有旧 gch，无论匹配、完整或有效与否；包括可确认归属的历史工具链缓存和失败残留，不涉及用户项目、外部编译器、另一安装。
- 新缓存必须与实际使用的编译配置兼容、确实命中，并有用户写题场景中的编译加速证据。

## 3. 所有权与最小改动

Runner 拥有编译参数、编译器选择和缓存生成策略；复用现有配置读取与参数校验，不在 Setup 或工作台复制一套编译默认值。Setup 拥有安装健康提示；工作台只负责齿轮菜单接入，调用扩展命令。构建工具拥有发行载荷及清单。

缓存仍在工具链目录，但它属于可变用户缓存，不是安装资产。完整性检查需要明确区分受管缓存与未知外来文件，不能简单放弃整个工具链目录的完整性验证。相邻位置沿用 GCC 原生查找规则，避免引入包装头、额外搜索路径和缓存选择框架。

## 4. 生成生命周期

1. 固定当前用户级 C++ 标准和编译参数快照，复用实际参数校验；固定本安装工具链和万能头位置。
2. 校验编译器、必要头文件、可写性和路径归属，取得同一安装跨窗口的独占生成权。前置失败不删除旧缓存；重复点击立即提示正在生成，不排队、不重放。
3. 显示右下角进度通知：“正在生成 gch 缓存，请勿关闭 BeCoder。”
4. 清除归属范围内全部旧 gch 和任务残留；`.gch` 文件及目录均覆盖，但不跟随链接或重解析点越界。遇到占用、权限或归属不明立即终止，不在未清理完时继续生成。
5. 用本次快照生成万能头缓存。必须从实际编译策略派生预编译头参数；排除源码、可执行文件输出等仅属于普通编译的参数，保留相关宏、语言标准、字符集及必要编译选项。debugger.h 的包含顺序须用命中和行为验证确定，不改变其既有功能。
6. 编译进程只写 GCC 不会误识别的临时产物；完成后验证并安全发布到相邻目标。不得让普通编译读到半写入 gch。存在真实并发读取时，清理或发布失败应明确失败，不能强删占用文件或破坏正常编译。
7. 验证实际编译路径命中新缓存；成功通知只有在生成和命中检查均通过后显示。失败输出简短原因并保留可查看的日志，不重建被移除的诊断页面。
8. 失败、中断或窗口关闭后终止本任务子进程，释放归属；残缺产物不得作为有效缓存。下次主动执行可清理自己的残留。锁恢复需确认原任务已退出，不能靠超时抢占仍存活的任务。

生成失败后不恢复已删除的旧缓存，也不自动重试。项目所有者于实施中明确简化：生成阶段失败后直接清空当前安装工具链范围内的全部 gch 和生成残留，不维护逐文件身份比对、并发替换文件保留或回滚机制。保留安装路径边界和不跟随链接越界的处理。参数等前置校验失败不清理现有缓存；初次清理失败直接停止，不重复盲删。

普通编译保留正常无缓存回退，不因缺少 gch 被禁止。生成期间更改设置不改变正在执行的任务；之后按新参数编译，不匹配时允许 GCC 回退，用户再次点击才重建。多窗口配置不同也不自动重建或排队。

## 5. 保护边界

保留 Runner、CPH、Notebook 的已有运行、取消、快照、证据和输入输出语义；不引入执行等待队列。保留 GCC 编辑器诊断、clangd、debugger.h 和原头文件。生成不修改用户源码、项目设置、外部工具链、环境变量或其他安装。

工具链目录不可写时明确失败，不自动提权、不另选缓存位置。删除诊断页后仍保留开发排错所需日志。中英文命令和通知同步；不扩展到 Beacon UI 或安装器重构。

更新及覆盖安装可能移除可丢弃缓存；不承诺跨工具链升级继续命中，不自动迁移或后台重建。

## 6. 验证与接受标准

- 受控回归：用户参数快照、宏及标准变化、非法参数、无旧缓存、损坏缓存、`.gch` 目录、旧版本缓存、链接越界、删除失败、生成失败、中断及重新执行、跨窗口重复生成、任务存活锁不得被抢占。
- 编译行为：无 gch 时默认 C++、含万能头题目和 debugger.h 正常；生成后实际 Runner、CPH、Notebook 编译路径均兼容；C 路径保持原样。检查缓存重建不改变程序输出或诊断边界。
- 命中证据：使用 GCC 提供的命中诊断确认真正读取 PCH，不能以生成进程成功、文件存在或单次变快替代。测试所用诊断参数不注入用户正常编译。
- 性能证据：相同编译器、参数、源码、磁盘位置分别测无缓存和命中缓存；分别预热后交替多次测量，报告样本数、编译耗时中位数和变化。至少覆盖轻量万能头程序及代表性的 STL 写题程序；比较编译阶段，不将运行耗时计入。未测量前不承诺固定倍数；没有稳定收益时回到实现诊断，不能宣称目标达成。
- 发布证据：源检查、扩展构建、staged application 和直接包验证须证明发行载荷及清单无 gch，必要原始头文件仍在，生成入口随产品交付；需要完整 Setup 验证时另按批准的实施计划执行。
- 界面接受：齿轮菜单位置、生成进度、成功及失败通知和损坏提示由隔离实例截图核对，再交项目所有者接受；构建成功不能替代此项。

## 7. 实现准备与停止条件

### 7.1 新增：简单 C 程序耗时异常

项目所有者报告：手动删除 gch 后出现预期的工具链损坏提示；之后 `.c` 和 `.cpp` 程序似乎都需要约 3–4 秒。测量边界是点击 Run 到 BC 终端输出 `===== Compilation Successful, Running =====`，属于体感总等待，并非编译器进程的实测时间。该现象尚未在受控条件下复现。

当前源码中 `.c` 使用 gcc.exe 和 C 编译参数，不强制包含万能头或 debugger.h；启动健康检查为异步调用，未发现 Runner 等待损坏通知关闭的直接路径。因此不能把此问题归因于缺少 C++ PCH，也不能以重新生成 gch 代替定位。

当前代码在运行编译器之前还会等待 BC 终端打开、保存及快照源文件、准备私有环境并清理旧的同名可执行文件；`compileMs` 只测子进程启动后到退出，`compilerSpawnMs` 单独测进程启动，而所报告的边界更早于编译成功横幅，不包括程序运行阶段。因此必须分段测量点击请求至横幅，而不能将体感时间直接等同于 gcc 编译耗时。

纳入同一轮的独立缺陷调查与修复项：先取得实际安装版本、实际命令及 BeCoder Runner Trace 的分阶段耗时，分别定位请求准备、终端就绪、编译器启动、编译/链接和发布至横幅的各段。对比同一 gcc.exe、同一参数和工作目录下直接编译的结果，区分首次与重复执行，并核对已安装代码与仓库基线是否一致。修复需有可复现的修前/修后证据；环境因素只能在证据支持后报告，不预先归因。

验收增加：无 gch 状态下简单 stdio.h C 程序及简单 C++ 程序从 Run 到编译成功横幅的分阶段耗时和重复执行对照，并单独列出纯编译耗时；不得要求用户生成 C++ 缓存来恢复 C 性能，不得以删减安全校验、快照或既有执行语义换取速度。项目所有者在实施中进一步确认：若 C 耗时现象未能复现，停止扩大调查，交付本次完整成品，不以复现为交付阻塞，也不宣称该问题已修复。最终成品包含 Setup 构建及直接验证；不发布、不修改当前安装。

书面设计批准后形成实施计划，列清 owning 文件、参数共用方式、并发与中断机制、具体验证命令及超时、产物和运行验收范围。遵循仓库验证预检和台账要求。设计稿不自动授权提交、推送、发布或清理现有构建产物。

若可靠并发清理必须大幅改动 Runner/CPH/Notebook 生命周期、需要脱离相邻存储、需要放宽工具链所有权规则，或性能验证无法证明收益，应报告具体证据并重新讨论边界，不悄悄扩展方案。
