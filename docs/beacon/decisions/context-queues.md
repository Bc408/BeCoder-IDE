# Beacon 持久化上下文：工具读取与近期队列修订

日期：2026-11-22。状态：负责人已确认的队列与取材决策记录。本轮已将这些决定直接合入[总体架构](../architecture.md)、[阶段设计](../foundation-design.md)、[代码工具](../code-snapshots.md)、[压缩设计](../context-compaction.md)及[执行计划](../../superpowers/plans/2026-11-22-beacon-foundation-implementation.md)。本文保留取舍追溯，不以临时覆盖提示代替现行正文。修订后书面稿及计划待负责人审阅，产品尚未实施。

## 1. 已确认的职责

负责人最新明确工作区选择与模式选择独立：只有发起窗口已选择Beacon工作区且当前根正常，软件层才生产并持久化用户行为材料；无根／根异常不采集、不写替代位置。有效根下Get Problem、Runner、CPH、Notebook、OJ Connect真实行为在Blackout也持续采集落盘，模式只裁切Beacon能否消费。Blackout禁止Beacon的持久来源目录／读取／调用写入，不禁止软件生产者写共享近期记录。用户切回Spot／Flood后可以读取队列仍保留的记录。该澄清不为Blackout聊天、代码工具或联网取题增加持久化副作用。

| 材料 | 触发与来源 | 保存和读取范围 |
| --- | --- | --- |
| Runner Run／Run With Input、CPH 测评、Notebook input 运行、OJ Connect 提交与实际取得的测评记录 | 既有真实用户行为，由原功能 owner 提供凭证；不依赖 LLM 或聊天已打开 | 当前 `.beaconWork` 内跨对话共享的近期队列，不是跨工作区的应用全局库；保留各来源结构 |
| 题目身份与题面 | 用户 Get Problem 保存题面正文及题目、代码文件、查看时间；底层同时提供文件名／目录和 CPH 关联线索，LLM 判断讨论对象 | Get Problem 队列限当前 `.beaconWork` 跨对话共享，上限 13 条，按题目与代码文件去重。默认读已保存题面；LLM 主动联网补取／刷新只将结果交给上下文，不另存或回写队列 |
| 当前对话代码快照 | LLM 主动调用获取当前编辑器代码的工具，harness 持久化同次实际取得的代码内容 | 当前对话私有队列，默认大小 10，单份完整正文最多 256 KiB（UTF-8）；队列自动淘汰，LLM 可直接列举和读取 |

负责人已明确回复：共享队列的“全局”是当前 `.beaconWork` 内所有对话共享。Get Problem 队列上限为 13 条，覆盖旧稿中该来源各 20 条的冲突表述；Runner、CPH、Notebook 和 OJ 结果各 20 条的原决定不因本次调整改变，不合并为混合总额。用户 Get Problem 的题面正文随该行为持久化；LLM 联网取题仅进入上下文，不增加题面存储机制。

代码快照唯一内容来源是上述真实工具读取，不从用户发送事件、模型重新生成的代码或从整段聊天中搜索拼凑内容生成快照。沿用完整原稿取舍；工具返回给模型的片段／分页覆盖仍须如实说明。运行记录中的执行稿继续作为原凭证的一部分存在，不自动另加入对话代码快照队列。

新问题发送不触发代码捕获。读取历史快照与读取当前编辑器是不同操作；是否需要新鲜代码由 LLM 选择。新读取含未保存修改，同一次读取、工具返回和保存正文必须对应同一真实版本，不以保存时的第二次读取替换第一次内容。

负责人已进一步认可代码队列的重复读取规则：

- 再次实时读取同一文件且完整内容相同时，复用队列内已有快照并移到队尾，不重复占用位置。
- 同一文件内容变化时新增快照；不同文件即使正文相同，也不按同一文件的规则合并来源。
- 读取历史快照不新增副本，也不刷新队列次序；同一快照的继续分页不产生新的代码版本。
- 复用以队列内仍可取得的真实快照为限，不为已淘汰正文增设查找库或额外保留机制。

负责人已认可读取成功、快照落盘失败时的交接：

- 工具仍返回实际取得的代码，LLM 可以据此继续回答；读取结果与保存状态分别反馈。
- 明确报告快照保存失败，不伪造保存成功或可读快照 ID，也不承诺后续从队列读回本次代码。
- 保存失败保留原有队列，不能因新快照写入失败而丢弃旧快照；包括失败的新写入或队尾更新，不先发布其淘汰结果。
- 保存失败不变成问题发送前置，不撤销已接受的问题。

负责人已认可代码快照的单份容量：

- 完整代码正文最多 256 KiB，即 262144 个 UTF-8 字节；计算正文，不以模型 token 数或 JSON 转义后的序列化长度代替。
- 超限时仍可按工具既有读取／分页能力返回实际代码，同时明确反馈未保存快照；不保存截断副本，不伪造可回读快照 ID。
- 超限不新增快照、不调整原队列或触发其淘汰；用户发送问题及当前代码读取不以快照保存成功为前置。

负责人已认可代码快照淘汰与分页的边界：

- 代码快照队列正常自动淘汰，不为跨次分页额外保留旧快照。
- 一次工具读取对应真实的固定快照身份；后续工具调用时，目标快照若已淘汰，明确返回已淘汰，不以新版补齐或拼接正文。
- 已实际返回的片段仍沿正常工具协议保留，不能据此声称完整快照仍在队列中。
- 队列内快照可读，但曾经列出的快照不保证始终可读。本项只针对本对话代码快照，不改变共享近期凭证既定的一致性读取规则。

负责人已认可编辑旧问题／重答后的代码快照范围：

- 代码快照按整个对话管理。编辑旧问题或重新回答不隐藏、删除或禁止读取原分支已经取得的代码快照，仍按默认 10 份队列和既定次序自动淘汰。
- 本对话代码快照目录及读取不依赖原分支工具消息仍处于有效历史；不额外维护分支与代码快照的可读关系。其他对话不能读取这些快照。
- 被舍弃分支的文字、要求、许可及其他分支私有材料仍按既有规则排除。历史代码可读不恢复这些内容，也不表示历史执行结果验证了当前代码。
- 负责人计划引入工具调用可视化，让用户看到 Beacon 实际读取代码的行为；本次保留规则尊重已经发生、并向用户呈现的读取事实，也避免为重答增加快照分支管理。该可视化是已提出的后续需求，尚未实现；具体界面另行设计。本次依据针对代码读取与快照留存，不改变其他操作既有的授权范围。

负责人已认可题目关联的职责分工，具体接口继续细化：

- 底层提供带来源的真实线索：用户 Get Problem 取得的题目标识及对应代码文件、CPH 已有的代码—题目关联，以及按现有规则由文件名／目录解析出的候选题目。
- LLM 结合当前用户提问判断正在讨论的对象；线索冲突且无法判断时，由 LLM 向用户询问。底层不以硬编码优先级替模型决定讨论对象，不把不同题目的材料悄悄合并。
- Get Problem 记录的语义已明确为用户实际看过哪道题、对应哪个代码文件和实际查看时间，提供给 LLM 作为行为依据，不替模型决定讨论对象。队列上限为 13 条，按“题目＋对应代码文件”去重：用户再次获取同题同文件时，更新最近查看时间并移到队尾；同题对应不同代码文件分别保留。
- 负责人已采纳：本地没有对应题面时，允许 LLM 主动调用工具，通过五站现有只读取题链路联网获取干净题面，无需用户再次手动 Get Problem；登录仍由用户完成，失败如实反馈。不会执行创建源码、导入 CPH 或展示／切换面板的完整 Get Problem 动作。具体接口字段与失败映射继续细化。
- LLM 补取题面是工具取材，不得伪造用户 Get Problem／看题行为，不更新用户查看时间或 Get Problem 队列次序；其实际来源与取得时点分别表达。负责人明确该联网结果只读入上下文，不另行持久化，不增加缓存、队列或独立题库，不因允许联网自动扩大后台采集范围。

负责人已认可题面正文的保存与刷新规则：

- 用户 Get Problem 的持久化记录同时保存解析取得的题面正文，不只保存题目标识、关联文件和时间。
- 默认读取用户 Get Problem 已保存的题面，向 LLM 返回实际取得时间与来源；用户看题时间与模型联网取得时间分别表达。
- 提供显式刷新能力，由 LLM 判断何时需要重新获取；不设置定时刷新或后台检查。
- LLM 刷新指重新联网取得本次上下文，结果不回写原有 Get Problem 正文。成功返回新的观测；失败反馈实际失败，已有持久化题面保持原样，不能把旧版称为最新或成功刷新。
- 无论本地是否存在对应 Get Problem 记录，LLM 的联网补取／刷新都不改变用户查看时间、队列次序或已保存题面，不增加专门持久化。用户后续再次 Get Problem 时，才按真实用户行为更新保存的题面与最近查看时间。

负责人进一步确认页面与事实来源边界：

- Blackout依旧能读取BeCoder本窗口已打开代码编辑页的正文（含未保存修改）、文件名和路径；不因关闭持久化来源而关闭该代码页能力，读取只返回上下文。
- 题面不通过读取编辑器内题目页面取得，直接使用OJ Connect只读联网解析能力；Spot／Flood已保存Get Problem题面仍可按既定规则默认消费，Blackout禁该持久来源而直接联网。
- Runner、CPH、Notebook运行结果、OJ Connect测评事实只以持久化记录作为唯一一等来源。Blackout下这些记录及Get Problem持久化能力对Beacon不可用，但软件层在有效根下仍照常采集落盘，其他档位同样不提供对应功能页面、终端渲染或Notebook页面投影的自动读取旁路。
- 关闭功能页面的事实投影不取消Notebook独立文档本身、明确请求的学习资产操作或用户主动提供的文本；它们保持原身份，不冒充系统采集的执行／判题凭证。当前未改产品实现。

## 2. 被本次决定覆盖的旧方案

| 旧方案或上一轮问题 | 最新处理 |
| --- | --- |
| 读取与独立沉淀拆成两次模型操作，LLM 另选时间调用保存 | 不再作为首版前提；模型主动读当前代码时，由 harness 保存同次取得内容 |
| 为稍后保存先前版本，跨工具调用保留未沉淀全文或设计引用期限 | 不需要；同次取得、保存与返回，不增加这类暂存 |
| 由 LLM 判断旧代码价值，再物理删除独立正文 | 改由每对话默认 10 份的队列自动淘汰，不依赖模型提出删除清单 |
| 编辑／重答后，所有原分支私有材料都按工具消息有效性限制读取 | 本对话代码快照例外：按整段对话的队列可读，不绑定有效分支；旧消息、许可及其他分支私有材料仍保持原隔离 |
| 压缩必须联合产出 summary 与 discardSnapshotIds | 该联合契约撤回；会话输入压缩和代码队列淘汰分别负责各自生命周期，预算／同步方式／有界恢复继续保留 |
| 题目只能依赖持久化显式绑定，禁止目录／文件名／CPH 关联推导 | 被多来源线索供给覆盖；无宿主强制优先级，LLM结合用户问题判断，真正不明才询问 |
| 所有五类近期材料一律各 20 条 | Get Problem 队列最新改为上限 13 条；其他执行与测评来源的原定数量保持 |
| 只能消费用户已取得题面，本地缺失必须让用户再次 Get Problem | 本地缺失时允许 LLM 通过现有五站只读取题链路按需补取，不触发完整拿题副作用，也不伪造用户看题记录 |
| 为模型联网补取题面新增缓存，或将刷新正文写回用户 Get Problem 队列 | 不采用；LLM 联网题面只进入上下文，用户 Get Problem 仍是该行为队列和已保存题面的更新来源 |
| 让负责人在“保存当前稿／保存过去工具全文”中替模型选择 | 问题已被新读取即保存链路消解；模型决定调用和读取对象，系统确保该次实际内容保存准确 |

上一轮 [就绪性复审](../sources.md#review-history)按其审查时点保留。R1 的两种保存来源选择不再沿用；R2／R3 为持久强绑定提出的补齐方式须按新识别链路重评，不能机械实施；R5 的压缩任务仍需补齐，但不再包含模型删除快照。其余真实提交身份、摘要有效性和整理阶段边界继续有效。

## 3. 本轮工程细化的落点

产品行为边界已由上述决定收敛。下列字段和查询形态已写入执行计划，作为本轮候选工程契约供统一审阅，不再要求负责人重复决定已定配额、保存来源或题目判断分工：

| 边界 | 需要说清的行为 | 讨论建议 |
| --- | --- | --- |
| 题目线索的供应接口 | 候选字段、查询对象、时点和失败状态 | 执行计划§2及Task5：分别聚合Get Problem、CPH、路径解析；各来源独立报错，推导与真实行为分开，无永久绑定库或宿主唯一裁定 |

单纯列队列只提供来源、时间、版本与可读入口，不自动把 10 份全文灌入每次模型请求。代码队列淘汰不抹去已存在的实际工具协议，压缩后的有效输入也不因独立文件仍在就自动加载全文。

负责人最新进一步明确：Blackout相对Spot／Flood仅作朴素能力裁切，所有持久化上下文来源的目录、读取、写入能力对Beacon不可用；软件层用户行为仍按有效工作区持续采集落盘；不建立内存版代码队列、替代引用或跨档补存机制。已打开代码编辑页正文／文件名／路径、主动材料与普通已加载对话沿既有能力使用，代码读取只返回上下文。原计划新增Blackout镜像内存队列的建议已撤回，执行层也须拒绝被裁切来源，不能借缓存绕过；其余既有草稿／会话规则保持。

### 3.1 题目线索与题面工具的候选细化

以下是本轮细化；其中用户查看语义、13 条上限、同题同文件去重、Get Problem 保存题面正文、默认读取已保存题面、LLM 显式刷新、本地缺失时只读联网补取及联网结果仅进入上下文均已获认可，其余接口建议尚未整体获批。

1. **以所讨论代码对象查询本地线索。** 复用上下文目录／工具入口，给出 Get Problem 的真实取得记录、当前 CPH 关联及文件名／目录的现有规则解析结果。每条保留题目标识、来源、对应文件、实际依据及本次查询时点；历史行为时间只用真实已有值，不以文件 mtime 冒充拿题时间。某次拿题记录说明曾经发生的行为，不能单凭“最近一次拿题”断言是本轮讨论对象。各来源的缺失或读取错误分别反馈，不让一种来源失败抹掉其他线索。查询不隐式联网、不读取代码全文或新建代码快照。
2. **LLM 根据提问选取所需题面。** 多条线索指向同题时可合并展示但保留各自依据；指向不同题目时分别提供。用户可明确问另一题或要求对比，模型按当前语意选择一个或多个对象。选择不反写 CPH、修改文件名或固化为永久绑定；目录中仍须保留真实来源。
3. **干净题面与完整 Get Problem 动作分开。** 题面读取入口接收明确支持的题目标识，返回结构化正文、样例、限制、语言／覆盖及实际取得时点。本地缺失时由 LLM 工具调用按需转交五站现有只读题面 owner，不执行会创建源码、导入 CPH 或打开／切换面板的完整命令，登录仍由用户完成。用户 Get Problem 持久化包含题面正文；默认复用已保存题面，并提供 LLM 显式联网刷新。模型补取或刷新结果仅进入上下文，不增加专门持久化，也不回写用户行为队列及其正文，无定时刷新。失败反馈实际状态，原已保存题面保持，不宣称旧版最新。
4. **关联推导与凭证真实性分开。** 推导可帮助发现当前问题的相关材料，但不改写旧执行或提交记录的原始题目、代码版本和判定。拿到题面不等于已核对当前代码；网页请求失败、需要登录、解析不全或题目标识不符，均反馈实际状态，不把失败当作成功空题面。

已核对的现有接点：OJ Connect 的 problemResolver 按配置站点目录及文件名解析 ProblemRef；CPH ProblemStore.load 已能按源路径取得既有题目元数据及 revision；OjAdapter.readProblem 与 browserHost 的只读题面调用链独立于 showProblem 的显示动作。这说明可以沿已有 owner 补窄接口，不表示 Beacon 已具备本节候选能力。
