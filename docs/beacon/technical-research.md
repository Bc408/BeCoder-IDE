需求依据为[正式 PRD](prd.md)、[架构基线](architecture.md)和[Notebook 设计](notebook.md)。本文规定研究顺序和证据要求，不是开发排期或已批准的具体实现。

## 1. 先研究上下文获取与工具组织

先回答：“用户直接问编译/运行问题时，Beacon 如何取得充分、对应正确且不越权的材料？”这直接决定导师回答质量，也为 Notebook 整理、压缩和记忆提供输入基础。

研究使用真实旅程，而非先决定工具名称：当前未保存编辑稿与旧编译快照不同；Runner 尚无输出；CPH 当轮多个样例；多题网页/PDF；本人同题多次提交；正文与 Notebook 最近结果。每个旅程检查材料生产者、读取入口、可观察事实、权限、版本与缺失。

比较成熟编辑器 API、当前模块提供受控记录接口、已有工具入口扩展等路线。CLI 式组织方向已定，具体入口数量与返回策略未定；不把“统一入口”自动等同于一个超大工具，也不预设摘要/详情必须分两轮。

本轮应产出：

1. 当前材料与调用链图，标清谁生产、哪些尚不存在。
2. 可复用机制清单和有证据的差距；外部源码记录固定提交、路径与许可证。
3. 两到三种工具组织方案，比较模型可用性、信息覆盖、token 开支、权限实施和宿主复杂度。
4. 用同一组场景检验方案，记录原始事实、实际送入材料、模型回答与失败原因。
5. 推荐方向及必要的产品取舍；普通接口细节由工程判断，不重复询问已定规则。

## 4. 各方案的共同检验标准

- 事实可辨：当次代码、当前编辑稿、历史提交、编译状态、实际输出、模型判断不能混淆。
- 范围正确：spot 独立根、外部单文件授权、blackout、敏感信息、OJ 账号许可与会话隔离均真实有效。
- 留存明确：队列、会话材料、摘要、记忆与 Notebook 不互相冒充；窗口和根变化不改旧资产归属。
- 用户资产保护：Notebook 最新完整编辑稿、运行交接、备份失败、生成/保存失败及取消具备可验证结果。
- 质量而非形式：同一批材料比较回答诊断、摘要忠实、tips 适用与笔记独立复习价值，文件写入成功不算教学成功。
- 真实成本：上下文体积、重复调用、延迟和 BYOK 兼容性用实测说明，区分平台 token 用量和价格估计。
- 复用可落地：确认许可证、Windows/Code - OSS 适配、维护成本与依赖；不把 API 存在等同于产品体验已满足。

验证先以只读源码、官方资料和授权范围内材料完成。涉及实际模型费用、登录后账号、安装依赖、可保留原型或产品改动时，应给出具体范围并按已有授权执行；本轮未发生这些动作。

## 5. 返回产品层的条件

已有共识不重新投票。只有证据揭示实质取舍时返回产品层，例如某模型无法可靠调用工具、某平台缺失核心详情、自动整理费用超过预期，或路径突然失效让已承诺的内容保护无法成立。

受限模型体验、自动调用告知/控制、dream 失败/取消、整体资产管理范围和不确定赛事情境等尚未冻结。研究分别说明事实、候选方案与推荐，再集中讨论。

## 6. 证据与验证边界

本地源码入口核对、文档 UTF-8/链接/结构检查和语义审阅只证明各自范围。尚未完成完整调用链、模型质量、真实 OJ 登录、GUI 或安装包验证；不能把本次文档提交当作技术方案已经通过验证。后续研究记录实际命令、输入、结果和限制，再进入方案评审与实施计划。
