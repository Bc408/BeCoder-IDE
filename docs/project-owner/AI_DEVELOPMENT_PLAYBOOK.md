# BeCoder AI Development Playbook

> 本文档只面向 BeCoder 项目负责人，用于组织与 AI 的开发协作。普通开发 AI 不应把本文档加入项目定向、强制阅读顺序或日常上下文；AI 应遵循 `AGENTS.md`、`BECODER_HANDOFF.md` 和 `develop-becoder` Skill。本手册帮助人作出授权、验收和推进决定，不定义产品行为，也不记录当前阶段状态。

## 1. 先描述体验，再讨论实现

向 AI 描述需求时，优先说明用户实际看到、触发和感受到的行为：

- 用户从哪里开始操作；
- 正常情况下看到什么；
- 失败、取消、重试和并发操作时看到什么；
- 哪些现有行为必须保留；
- 哪些系统、项目文件或用户数据绝对不能受影响；
- 最终由谁、用什么方式验收。

当视觉或交互难以用文字表达时，提供截图、录屏、参考程序和具体示例。参考对象只证明目标体验，不自动授权照搬其架构、依赖或数据边界。

## 2. 调研、方案和实施分开授权

把一次复杂工作拆成明确阶段。每个阶段只授予当时需要的权限。

| 阶段 | 推荐授权 | AI 应交付的结果 |
| --- | --- | --- |
| 只读调研 | 允许阅读源码、文档、Git 状态和参考材料 | 当前事实、调用链、所有权边界、冲突和风险 |
| 方案磨合 | 不写代码 | 用户体验、删除项、保留项、失败边界、测试和验收方案 |
| 实施 | 只允许约定范围内的源码或文档修改 | 聚焦改动、对应测试、持续进度报告 |
| 源码验证 | 明确允许指定检查 | 逐项命令、退出码、失败分类和未执行项 |
| 构建与打包 | 单独授权 | 新构建产物和直接包校验，不替代 GUI 验收 |
| GUI 验收 | 默认由项目负责人执行 | 真实用户体验结论和需要继续打磨的细节 |
| 归档与备份 | 验收后单独授权 | 当前文档、归档记录、限定范围的提交和推送 |

“给出方案”“检查一下”“准备构建”都不等于授权修改、构建、提交或推送。新的授权应说明允许做什么，也应说明到哪里停止。

## 3. 要求 AI 先证明理解

复杂任务开始前，要求 AI 用当前文档和仓库证据回答：

```text
产品理解：
相关所有权边界：
当前仓库和阶段事实：
本次改动及其归属：
明确保护或排除的行为：
验证和项目负责人验收边界：
```

如果回答只重复需求、没有指出保护边界，或把历史归档当作当前事实，应先纠正理解，不进入实施。

## 4. 方案磨合到可验收颗粒度

一份可执行方案至少应明确：

1. 用户可见行为和准确文案；
2. 负责该行为的模块、进程和数据所有者；
3. 必须保留的普通功能；
4. 明确禁止恢复或引入的能力；
5. 成功、失败、取消、并发、重启和清理路径；
6. 中英文、主题、扩展、构建、打包和许可证影响；
7. 自动化验证与人工 GUI 验收的分界；
8. 本阶段不处理但需要记录的后续事项。

对于删除工作，要求 AI 按注册、消费者、运行路径、构建入口和成品资源判断归属，不能按关键词成片删除。对于文件系统工作，要求它说明路径所有权、链接或重解析点、并发替换、失败清理和恢复顺序。

## 5. 控制实施过程

实施期间要求 AI：

- 在修改前说明准备改哪些文件及原因；
- 保留工作树中不属于本任务的既有修改；
- 不直接编辑生成目录和依赖目录；
- 不擅自清理、重装依赖、改变系统环境或操作系统 VS Code；
- 遇到需求冲突时先停下来报告；
- 长时间工作时持续给出简短、可核实的进度；
- 用户说 `stop` 或“先停下”时立即收尾当前原子操作并停止继续推进。

当 AI 开始扩大范围、顺手重构、设计未来兼容层，或把“更完整”当作默认目标时，应把它拉回已经确认的产品边界。

## 6. 让验证先证明命令本身可靠

正式验证前，要求 AI 先完成只读预检：

- 从 `AGENTS.md`、仓库脚本或真实存在的工具入口确定命令；
- 检查命令、模块、配置和输入文件确实存在；
- 按 Git 状态区分新增、修改、重命名和删除文件；
- 确保解析器和 linter 不接收已删除文件或目录；
- 先检查复杂 PowerShell 的解析、插值、引号、编码和路径处理；
- 记录工作目录、超时、预期副作用和停止规则；
- 冻结正式命令列表，不在失败后静默换工具继续。

以下情况属于验证编排错误，不是源码错误：命令入口不存在、依赖模块缺失、Shell 语法错误、工作目录错误、输入文件枚举错误。它们必须如实报告，也不能算作目标检查已通过。

正式验证开始后，非零退出或超时应按项目停止规则中止后续流程。修复后先跑最小相关检查，最终再对最终工作树跑完整要求矩阵。

## 7. 要求结构化失败报告

验证失败时，可以直接要求 AI 按以下格式汇报：

```text
失败命令：
工作目录：
原始核心输出：
目标验证器是否真正启动：
失败分类：编排 / 源码 / 包 / 运行时 / 外部环境
技术判断：
尚未执行的检查：
哪些旧结果已经失效：
建议的下一步：
本轮是否修改了文件：
```

警惕以下说法：

- 把“找不到命令”写成“类型检查失败”；
- 把解析器没有启动写成“文件语法有误”；
- 失败后换了另一个工具，却没有说明原命令无效；
- 使用修改前的测试结果证明修改后的工作树；
- 只有构建成功就声称 GUI、运行时或安装行为通过。

## 8. 独立审查不是形式步骤

高风险或跨模块改动完成后，要求独立只读审查者检查需求完整性、普通功能回归、失败路径、并发竞态、测试真实性、语言同步和打包边界。

主开发 AI 修复发现后，应让同一审查者重新核对。后续又发生实质修改时，之前的结论不能自动覆盖新改动。最终结论应明确是“无阻断问题”还是仍有已知风险，而不是笼统写“审查完成”。

## 9. 人工验收和产品交付

自动化检查只能证明其实际覆盖的层级：

- 源码检查不证明成品内容；
- 应用构建不证明 Setup 行为；
- Setup 直接验证不证明 GUI 和真实使用体验；
- 旧成品不证明当前源码；
- AI 的自动操作不替代项目负责人的主观视觉和交互验收。

人工验收时，记录具体场景、输入、观察到的结果和不满意的细节。只有项目负责人明确认可后，才进入归档和云端备份。

## 10. 归档和朴素备份

归档前要求 AI：

1. 更新当前状态和相关现行契约；
2. 记录最终验证、人工验收、剩余风险和下一步；
3. 保留历史事实，不用新决定改写旧归档；
4. 复读文档，检查当前状态、契约和归档是否冲突；
5. 等待单独的 Git 授权。

“朴素云端备份”只意味着限定范围的提交和指定分支推送，不自动包含 PR、Release、标签、发布说明或额外清理。

## 11. 常用提示词模板

### 只读调研

```text
当前只允许只读调研，不写代码、不改文档。请从当前权威文档和源码追踪真实调用链，说明现状、所有权、风险、保护边界和可选方案。无法从仓库或我提供的证据确认的部分，不要猜测。
```

### 方案磨合

```text
当前只修订方案，等待我确认后再实施。请明确用户可见行为、负责模块、保留项、删除项、失败与取消路径、验证标准、人工验收和明确不在本次范围内的事项。
```

### 授权实施

```text
我确认上述方案，授权在约定范围内修改源码和对应测试。修改前先说明文件范围；不要构建、启动 GUI、清理、提交或推送。遇到需求冲突或非预期工作树变化时先报告。
```

### 授权验证

```text
允许执行已确认的源码验证。正式执行前先做命令和输入预检，冻结命令列表。任一正式检查非零退出或超时时立即停止，保留原始核心输出，分类失败并列出未执行项，不自动换命令重试。
```

### 授权构建

```text
允许按当前文档规定的顺序构建和直接校验。构建授权不包含清理、环境修改、GUI 验收、提交或推送。完成后把产物交给我验收，不要代替我声明用户验收通过。
```

### 授权归档和备份

```text
我已完成验收并认可本阶段。允许更新当前文档与归档，随后只对本阶段范围作一次普通提交并推送到指定分支。不创建 PR、Release 或额外发布流程。
```

## 12. 项目负责人检查清单

在允许 AI 继续下一阶段前，快速确认：

- AI 说清了当前事实与历史记录的区别；
- 产品所有权和保护边界没有被模糊；
- 本轮权限明确，未默认包含构建、GUI 或 Git；
- 验证命令有仓库依据，输入和依赖已预检；
- 失败被分到正确层级，没有把工具错误嫁接给源码；
- 修复后的最终工作树有对应的新验证证据；
- 独立审查覆盖了最后一次实质改动；
- 自动化、成品验证和人工验收没有被混为一谈；
- 归档和备份只在明确验收与授权后发生。
