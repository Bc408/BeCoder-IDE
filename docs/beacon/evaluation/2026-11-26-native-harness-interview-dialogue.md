Beacon 原文：

## 结论：最值得检查的是 `a[mid] == x` 时的处理

题面要求输出「**第一次出现**的编号」，而你第 15–17 行是：

```cpp
if (a[mid] == x) {
    answer = mid;
    break;        // ← 问题在这里
}
```

这是「判断 x 是否存在」的写法，它并没有找「第一个」。二分过程中第一次撞上的 `mid` 只是**某个**等于 x 的位置，可能靠右。

## 用题目样例就能验证

`a = [1,3,3,3,5,...]`（下标从 1 开始），查询 `x = 3`：

| 轮次 | l | r | mid | a[mid] | 动作 |
|---|---|---|---|---|---|
| 1 | 1 | 11 | 6 | 7 | 7 > 3，r = 5 |
| 2 | 1 | 5 | 3 | 3 | 相等，记为 3 并 **break** |

输出 `3`，而正确答案是 `2`。样例期望 `1 2 -1`，所以第一组数据就会出错——不用等大数据。

## 思路上的区别

- 你现在的写法是“在区间里**找一个**等于 x 的位置”，找到即可停止。
- 题目要的是“在区间里**找满足 a[mid] ≥ x 的最左位置**”（二分答案、找边界），而两者的判断条件形式不同：

二分边界类问题里，`a[mid] == x` **不是一个终止条件**，只是一个“和小于、大于一样普通”的分支。相等时你必须**继续往左半区间看**，因为左边还可能有更小的合法答案。

所以等号分支应该改成像“记录 + 收缩右侧”的形式，例如：

```cpp
if (a[mid] >= x) {      // 注意这里是 >=，不是 ==
    answer = mid;       // 先记下候选
    r = mid - 1;        // 继续往左找有没有更早的
} else {
    l = mid + 1;
}
```

循环结束后 `answer` 是「第一个 ≥ x 的位置」，但它**不一定等于 x**（x 可能根本不存在，此时它指向第一个比 x 大的数），所以还需要一次判断：

```cpp
if (answer == -1 || a[answer] != x) answer = -1;
```

（你初始化的 `answer = -1` 正好可以复用；注意 `n` 可能为 0 的情况在此题不会出现，`1 ≤ n`。）

## 顺带确认没问题的部分

- 下标统一用 1 开始、`a` 开成 `n+1`，和题目编号一致，不用换算；
- `int` 足够（下标 ≤ 10⁶，值 ≤ 10⁹）；
- `ios::sync_with_stdio(false)` + `cin.tie(nullptr)` 满足这题的大输入量要求；
- 外层 `while (m--)` 每次重置 `l, r, answer`，没有跨询问污染。

改完等号那一支后，建议先手跑一遍样例，再自己造一组「x 在数组最左端」和「x 比所有数都大」的边界数据。要的话可以贴回来，我帮你看边界有没有遗漏。

## 出错的是哪一类查询

| 询问 | 特征 | 二分到手的位置 | 结果 | 判定 |
|---|---|---|---|---|

## 对「刚才那个问题」：逻辑上确实解决了

上次的失败类型是「值存在且多次出现，撞到的不是最左那个」。现在 `a[mid] == x` 不再终止，而是**记录候选并把右界压到 `mid-1`**，即把等号变成「和大于一样」「丢弃右侧」的分支。这满足左边界二分的性质：

- 丢弃右侧是安全的：右边任何位置都不比当前候选更小；
- 丢弃左侧（`a[mid] < x`）也安全：单调不减下，`[l, mid]` 全都 `< x`，不可能是答案；
- 每轮 `l` 或 `r` 至少动一格，必然终止。

手推这次样例（`answer` 初值 -1）：

| 询问 | 收缩过程 | 结束 | 输出 |
|---|---|---|---|
| `1` | mid=6(7>1)→r=5；mid=3(3>1)→r=2；mid=1(1==1) 记 1、r=0 | l=1>r=0 | 1 ✅ |
| `3` | mid=6(7>3)→r=5；mid=3(==3) 记 3、r=2；mid=1(1<3)→l=2；mid=2(==3) 记 2、r=1 | l=2>r=1 | 2 ✅（原来错在这里） |
| `6` | mid=6(7>6)→r=5；mid=3,4,5 均 <6，l 一路推到 6 | 区间空 | -1 ✅ |

三点值得留意：

1. **不需要再补 `a[answer] != x` 的校验**——这是它和我上次贴的 `>=` 写法的区别。`>=` 版本会记录「第一个 ≥ x 的位置」，可能压根不等于 x，所以要补校验；你现在是显式判等，`answer` 只可能被写成真正相等的位置，补了反而是冗余的一步。
2. `else` 同时兜住 `a[mid] > x`，正确。
3. 只改了这一处，`l/r/answer` 的初值、1 基下标、IO 加速都没动，没有引入新的越界或类型风险。

现在的状态是：官方样例 3/3 通过、边界与重复值都被判题证据覆盖，算法本身可以认为定案。真正还悬着的不是正确性，而是**「你能否在下一次不需要这次这么长的往返」**。

建议把这个骨架当模板固定下来，只换「判断条件」：

```cpp
int l = 1, r = n, ans = -1;
while (l <= r) {
    int mid = (l + r) / 2;
    if (/* 条件 */) { ans = mid; r = mid - 1; }   // 往左收，记录候选
    else            l = mid + 1;                  // 往右推
}
```

同一份骨架可以覆盖三类常见需求：

- **第一个 `a[i] >= x`**：条件写 `a[mid] >= x`，结束时 `ans` 就是答案，**不需要判等**；
- **第一个 `a[i] > x`**：条件换 `a[mid] > x`，等于「第一个 ≥ x+1」，可用来算 `x` 最后出现的位置；
- **`x` 出现次数**：`(第一个 > x 的下标) - (第一个 ≥ x 的下标)`。

要注意和各写法的**返回值语义**绑定使用：`>=` 版本结束时 `ans` 可能指向一个不等于 `x` 的位置（所以要么判等，要么它本身就是你要的「插入点」）；你现在这版是显式判等，`ans` 只会在真正相等时被赋值，因此不需要补 `a[ans] != x`。这两者混用是这类题最常见的错。

不必须但值得试：把 `P2249` 改成用 `std::lower_bound(a.begin()+1, a.begin()+n+1, x)` 写一遍，和自己手写的版本对拍同一批输入——能直接看出手写版的返回语义是否和标准库一致。
