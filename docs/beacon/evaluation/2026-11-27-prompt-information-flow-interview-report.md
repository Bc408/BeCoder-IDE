# Beacon信息流提示词：原生访谈与核验

日期：2026-11-27（Asia/Shanghai）。[Beacon访谈原文](2026-11-27-prompt-information-flow-interview.md) · [完整33轮问答](2026-11-27-prompt-information-flow-interview-dialogue.md) · [问题矩阵](2026-11-27-prompt-information-flow-interview-plan.md)。

**Beacon最认可的是分层执行记录、捕获代码和Notebook身份信息；它最想补充的是“产品怎样取得编译源码”的事实。** 这些反馈有具体经历支撑，值得优先阅读。工程核验同时表明：记录已正常提供时，模型仍会选错历史事件、串联代码版本，或在正确材料上扩大结论。本轮不支持宣布整体回答质量已经稳定。

建议先读访谈F03、I01、I02、I06、F02，再对照工作W07／W07A、W10、W12。全部访谈逐字保留；本文的开发建议与Beacon原话分别标示。

## 1. Beacon的意见及我们的理解

| Beacon的实际反馈 | 对应经历与核验 | 下一步可讨论的处理 |
| --- | --- | --- |
| **保留“层次＋原因＋捕获代码”**。F03称这是最省力的部分 | W04拿到编译失败、诊断、not-run及原因，能定位缺分号并区分输入已准备与未执行。这是现有记录可解释性的正面证据 | 保持运行owner、采集适配和固定投影的分工；不因模型个别误用拆散记录 |
| **保留单元格ID、位置和代码哈希**。I01／F03把Notebook调序选为最值得回放的片段 | W09／W10取得全本内容及两条运行，主体对应正确；当前ID用于两次现场读取之间认同一格，历史位置与代码用于解释旧执行 | 保留现有事实身份。它称“唯一线索”“唯一归属陷阱”过强：旧源码正文也可对照，且W07已实际选错事件。不要据此新建快照或绑定系统 |
| **CPH配置定位存在探路开销**。I02认为根目录列表帮助很小，找到`.cph`和读正文才有决定性价值 | W05以4次inspectFile取得源码旁的真实`.prob`，没有错误路径或范围失败；CPH产品主题已有存放位置，但该轮没读取该主题 | 优先复核产品知识入口是否容易发现，不直接增加CPH配置工具，也不把一次探路称为接口缺陷 |
| **截断释义有用**。I03／F02指出“后缀不在此记录”避免把截断误解为可续读 | W08确实按保存前缀收窄结论，没有反复读同条记录求全文；不能证明说明是减少调用的唯一原因 | 保留在实际截断字段旁的说明；不要搬进system统一讲所有异常 |
| **不知道编译源来自磁盘还是缓冲区**。I05反复提及，I06主动撤回“多半跑旧版” | 源码表明Runner会保存dirty文档，CPH在编译前保存源码。模型当时并未读取runner／cph产品主题，已读的notebook主题不能回答这个问题 | 可讨论在runner／cph主题补充真实保存／捕获语义，再验证可发现性；暂不采纳F03提出的新来源字段。现有执行稿已能说明实际用了什么文本 |
| **希望Runner可带期望输出或至少说明是否判分**。F03将合流、截断和无check并列为阻力 | 返回notes已明确Runner不自动判题；CPH承担答案检查。记录已按设计表达merged与截断，材料缺口符合产品分工 | 保留这份真实感受，暂不据此扩张Runner业务或增加重复字段。需要判断的是模型为何仍觉得“不知道是否判分” |
| **目录已能预判不可读目标**。Blackout的F01承认两次readPage尝试多余 | W17对后台C++和无provider提交页的读取被拒；没有取得代码或判题正文。F01也承认忽略了可见P1001，并把旧位置推算说得像已知 | 继续核对目录、工具范围和失败反馈三处含义的一致性；权限门禁应保留，不开放功能页回读旁路 |

这些建议来自有限实际体验，不能把所有“不够用”解释成缺功能。特别是Runner未判题、隐藏输入不可见、截断后缀不存在，都是当前承诺范围；调优重点应是帮助模型自然理解这些事实及其分工。

## 2. 自述本身也需要核验

**I03把后来取得的产品知识当成早期回答的原因。** 它称Notebook产品说明决定了W09的运行对照和W10的调序解释；实际首次读取`notebook`与`overview`是在W16。F02补核后明确撤回，并指认早期真正可查的依据：readCurrentCode和run结果旁关于全本位置、执行时位置的notes。

这支持本轮“字段含义在实际返回时出现”的设计方向，但不能用修正后的回忆覆盖I03原答，也不能由一段自述证明提示改动的因果效果。F02说readBeCoderInfo“只调用过一次”仍不精确：它指同一批次，实际是两次调用、两个主题。

**I06的自我纠正有价值，但理由仍不完全准确。** 它主动撤回了“dirty导致CPH多半编译旧版”，收窄为未知。工程核验给出了更明确的答案：Runner与CPH有显式保存步骤；自动保存关闭不会取消该步骤。isDirty读数随真实保存变化，本轮没有证据表明该字段失真。

**I07把服务错误定位为“回答投递失败”，证据不够。** W19已完成readProblemRecord，后续宿主报告“暂时无法连接服务商，请稍后重试”，无答文。仅凭该字符串不能确认失败发生在生成、服务端处理或传输的哪个阶段。W19A复用已取得事实完成回答，可以确认恢复结果，不能反推精确原因。

## 3. 取得材料以后仍有的明确错误

以下经过主agent复核及独立只读子agent核验，不是用成功调用数推导的质量评分。

| 回合 | 实际问题 | 判断 |

| **W12** | 正确读取AC、100分及六点结果，又说“含大规模数据”“边界情形由官方数据覆盖” | verdict没有隐藏输入、具体规模或边界类别。末尾承认看不到数据，不能抵消前面的确定断言 |

另有较小但值得保留的例子：W02手推写`a[6]=9`，实际为7；W08未读现场却沿用“当前仍是dirty中点改写稿”，实际此前已恢复并保存；W09对可直接手算确认的输出仍说“只是看起来对”。前两项是细节与时效错误，后一项把缺少自动检查扩大成推理不能下结论。

回答还频繁展示记录ID、哈希、status和毫秒表格，往往超出用户问题所需；这些信息有助于内部核验，不应在每份教学回答里机械搬运。不能通过删去真实字段来证明输出会自然变好，宜保留同场景评测后单独讨论表达取舍。

## 6. 下一步建议与交付边界

1. **先由负责人审阅Beacon原话和上述反证。** 优先判断“编译源码怎样取得”这项产品事实应放在何处；可在runner／cph主题精确补充现行行为，避免新增与实际代码正文重复的字段。
2. **把“新运行后连续追问”作为首要选材样例。** 保留W07、W07A及W08真实发布／读取时间，检查复用与更新依据，保留必要澄清空间。不要恢复讨论对象绑定、每轮强制刷新或发送hook。
3. **单独审阅取得材料后的结论强度与表达。** 用W10位置串位、W11版本混同、W12隐藏覆盖外推和I03因果倒置作少量共性评测；prompt保持分层，不逐例堆成手册。保留工具结果旁的短释义，模型的事后建议本身也要过事实核验。

本轮仅交付访谈与核验，未实施这些建议，未修改生产代码或提示词，未新建stage、Setup、Git提交或推送。实例保留在Spot主会话，供负责人翻阅；实验profile、真实队列和合成练习稿继续保留。本机原始证据位于`.superpowers/sdd/2026-11-27-beacon-prompt-interview/`；公开文档中的可见导出不含内部推理、密钥或认证信息。全部访谈逐字保留，W15仅对外部英文引文作显式省略。

交付核验：33份可见导出与原始收据对应，11份访谈答文逐字一致；49次调用配对、三队列及记录大小复算通过。223项生产源码／资源／bundle输入、748份编译owner文件与准备时绑定一致，正式stage、基线副本及访谈插桩副本的Beacon bundle分别核对通过。证据／链接审计、仓库文档结构校验及tracked diff空白检查均退出0；没有因本轮纯文档与访谈工作重新运行源码测试或构建。另一位独立只读审阅者复算分母、访谈原文与报告归因，未发现阻塞问题。精确命令与收据保存在同一实验目录的`validation-plan.json`、`validation.jsonl`及`evidence-audit.json`。
