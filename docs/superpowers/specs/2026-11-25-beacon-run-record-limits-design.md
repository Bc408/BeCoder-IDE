# Beacon run记录字段截断与单条容量限制

日期：2026-11-25。状态：负责人已批准并授权实施；实施计划见同日plans目录，实现与验证结果见Beacon实现状态。本文收敛既有采集、入队和读取链路，不新增工具、队列或存储系统。

产品基线为`Beacon_Next@950befec109132e25c190d896e8375a17a04ef0a`。工作树已有本轮原生访谈文档，予以保留；本方案不包含Git提交或发布。

现行合同从[Beacon入口](../../beacon/README.md)、[底层设计](../../beacon/foundation-design.md)、[工具合同](../../beacon/tool-contract.md)及[实现状态](../../beacon/implementation-status.md)读取。负责人本轮决定替代旧run容量规则；本方案已获批准，但实际交付与验证须以实现状态为准。

## 1. 目标与已确认取舍

真实工作中，一份run的输入正文为1,600,017 UTF-8字节。工具完整读取后，后续模型请求和普通续问在本地容量准备阶段失败；既有8KiB仅限制编译及程序输出，未限制输入、期望值和源码。证据见[原生访谈报告](../../beacon/evaluation/2026-11-25-native-harness-interview-report.md)。

本轮解决run采集正文无界增长，并明确超大记录的入队与读取失败。不把这项修复扩大成压缩算法重构或提示词调优；先前已经进入聊天历史的大工具结果，不因新增采集规则而自动变小。

负责人已确认：

- 取消整条2KB、16KB方案；新run单条上限为32KB，即32,768 UTF-8字节。
- 长文本按字段字符数量独立限制；不引入输入／期望值／程序输出共享额度，也不保留编译流之间的共享额度。
- 朴素保留开头，发生截断时明确标记；不再保存头尾或重新分配剩余额度。
- 字段截断后，整条记录仍超限则明确报错、不入队，不继续删减内容凑大小。
- 源码尽可能保留，给予高于输入输出字段的独立额度。

## 2. 字段上限

每个字段独立计算，不跨stream、input、测试点或整条记录分配字符额度。

| 字段 | 上限（字符） |
| --- | ---: |
| program.code | 8,192 |
| runs[i].input.text | 4,096 |
| runs[i].expectedOutput | 4,096 |
| runs[i].output.stdout／stderr／merged | 每个实际存在的字段各4,096 |
| compile.output.stdout／stderr | 每个实际存在的字段各4,096 |
| record.error、compile.error、runs[i].error | 每个字段各1,024 |

编译流各4,096与error各1,024是本次移除所有共享额度后的具体工程表达，已随本方案获批。原8KiB输出共享算法退出，不与新规则叠加。先前提出的32,768字符输入输出共享额度撤回。

字符按Unicode码点计数；普通汉字、英文字母和换行各计一个，不将UTF-8字节数冒充字符数，不截断代理对。CRLF分别包含两个码点，不额外改变原换行。截断文本保持原前缀，不加可能被误认为原程序输出的省略号。

完整文本保留字符串；发生截断时，统一表达为`{"text":"保留下来的原文前缀","truncated":true}`。未知交互输入仍是null，不伪装为空字符串或截断结果。上游执行器已省略输出时，即使Beacon取得的片段未超过字段上限，也应保留内容不完整的事实；不得写成完整输出。

该结构只用于采集后的run正文。源码、输入和输出的执行owner仍消费其原始数据，不能把截断后的源码回送编译，也不能把截断后的期望值送入CPH检查器。路径、ID、状态、时间、退出码、check、序号和编译参数不按正文规则截断；这些信息造成超限时走整条拒收。

## 3. 处理顺序与所有者

1. 执行层按既有逻辑编译、运行、检查、取消与清理。
2. Beacon采集适配器取得真实执行信息，对上述长文本字段独立保留前缀。流式编译和程序输出只累积必要前缀，并记录是否有后续正文被舍弃，不为无限输出先积累完整文本。
3. 结束后组装run，保留实际状态及所有测试点的身份，不截掉数组元素来凑大小。
4. 存储入口分配ID并进行最终检查：`UTF8(JSON.stringify(record))`不超过32,768字节。计算包括字段名、标点、转义字符、ID和截断标记，不包括队列外壳及其他记录。
5. 超过32,768字节则返回专门的记录超限错误；等于上限允许。失败不执行队列写入，也不提前淘汰旧记录。
6. 允许入队后仍复用现有锁、原子写入和30条近期队列；无第二份原文库，不另存旁路文件。

采集适配器与存储入口复用小型字段规则／检查函数，不各自维护不同额度。错误应明确说明“本次运行记录超过32 KB，未保存到Beacon上下文”；原生运行结果、网页判词及用户文件不因此失效。一次拒收报告一次，不自动排队、重跑或重发。

不同来源保留已定形态：CPH运行stdout／stderr分流，Runner和Notebook运行merged；编译输出沿实际stream保存。规则只影响Beacon证据，不改变各模块运行限制、展示内容或Notebook每程序一次编译行为。

## 4. 工具、存量记录与会话边界

readRunRecord的参数仍为可选id，空参列目录，带ID读取；不增加offset、part、include、按题过滤或新工具。模型看到明确的截断标记，不把不完整源码或I/O当作完整原稿。工具说明只补必要的结果语义，不向system加入操作手册。

存量记录采用以下最小边界：

- 不自动迁移、重写或删除用户旧run队列、旧对话或工具交换。
- 新增记录执行新规则；现有旧结构仍能被识别，不因引入新限制把整个队列判为损坏。
- 旧记录的目录可以正常列出；按ID读取旧记录前也检查32KB。超限返回单条明确的容量错误，不把巨大正文送入模型，不使其他记录或后续新记录无法访问／入队。
- 不为兼容旧记录另建索引、镜像或后台压缩任务。旧队列按正常近期淘汰规则更新。
- 已进入某段聊天历史的巨大工具结果仍属于历史容量问题。本轮不静默修改原交换、不自动编辑用户问题，不宣称已修复全部压缩和续问恢复问题。

这意味着旧的大记录不会被悄悄改成新截断稿，而是明确拒绝正文读取；新采集的大输入会先按字段截断，再决定能否入队。

problem13／verdict20及其正文规则、run30及单位、工作区采集与模式消费边界继续沿现行合同。readCurrentCode仍读取现场完整代码，不能把历史run的8,192字符限制扩展到当前代码工具。fetchProblem、模型输出预算、90%压缩线、60%目标及一步一次恢复不在本次调整范围。

历史评测报告保留当时8KiB规则与失败数据；只在现行合同中替换已过期要求，不能改历史报告制造“当时已修复”。

## 6. 验证与验收

先用聚焦回归验证以下行为，再进行拥有者类型检查、OI统一编译和新stage构建。实现前从package脚本确认精确命令和依赖，记录台账。设计文档检查不冒充产品检查。

- 每字段等于上限、超过一个字符；中文、emoji、跨字节stream分片、CRLF；正确保留原文前缀及截断标记。
- 每个编译／程序stream独立，某字段短不把额度转给其他字段；多个input也不共享或回配。
- 大量编译报错、循环输出和1.6MB输入均有界；状态、check和退出码保持执行事实。
- 完整JSON恰好32,768字节可入队，超过一字节拒绝；计入ID、转义及标记；原队列内容不变。
- CPH多点、Notebook多input、多程序和取消保持既定粒度。过多测试点使整条超限时明确拒收，不丢测试点冒充完整记录。
- 旧正常记录可读；旧超大记录返回单条错误，目录和其他记录仍可用，新采集不被旧记录阻塞。
- 新run被模型读取后，实际大输入不再以完整巨大正文进入请求；用真实模型验证可解释截断、继续回答。单条被拒收时不误报“从未运行”。
- 原生编译、运行、CPH判定和Notebook展示未被Beacon截断污染；Blackout的采集资格／消费权限继续分离。

验收成果为源码检查、聚焦运行证据和新的stage候选；负责人体验验收另列。旧会话容量恢复、其他工具的大内容、模型预算／压缩异常分类继续作为独立问题，不用本轮run修复推断已经全部解决。
