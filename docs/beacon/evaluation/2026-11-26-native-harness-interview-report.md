## 3. 先核查业务动作，不为缺记录马上加状态系统

实验侧直接给`.cph/*.prob`补入两个测试，然后调用`becoder.cph.runTestCases`，命令返回后没有新run。W08如实查不到。随后显式执行`becoder.cph.openCurrent`再调用测试全部，才产生开始时间`00:26:38.191Z`的新记录（三组passed）。原命令时间是`00:24:36Z`。

**现场只证明第二次动作产生了新运行，不证明第一次运行延迟入队。** 外部改写配置后未重新打开owner，可能使旧revision与当前文件不一致；另一方面，`runSource`在已有view分支把动作转发为Webview的`requestRun`后即返回，返回本身也不证明编译开始。该操作不是单纯通过CPH正常编辑按钮完成的用户场景，不能把这一夹具摩擦直接定为软件正常点击缺陷。

相关源码：[命令入口](../../../extensions/becoder.cph/src/extension.ts)、[runSource与面板握手](../../../extensions/becoder.cph/src/judgeView.ts)、[配置revision验证](../../../extensions/becoder.cph/src/judgeSession.ts)。未保存首次拒绝的确切UI提示或完整Webview消息，不能进一步认定是哪一分支。后续若处理，应先在正常面板编辑流程以及隐藏／重开面板下独立复现，区分未受理、配置变更拒绝、执行失败和采集失败。实验驱动今后应等真实新记录或明确失败后再描述“已跑完”，不能只等命令返回。

Beacon提出的pending可见性有合理使用动机，但当前已确认的队列只保存结束事实；本轮没有足够证据改变该合同。**优先修可复现的业务或实验编排问题，再决定是否真的缺模型上下文。**

## 4. 最值得继续讨论的少量改进点

1. **合流与分流的事实表达。** 保持三个来源真实差异，先考虑工具说明一句话标清“编译诊断独立，Runner/Notebook程序输出合流，CPH分流”；以本轮I09作固定评测，检查模型是否仍拿编译stderr推断程序stderr。不复制整篇产品手册。
2. **同文件多个可见页的重复正文。** 核查原生枚举是否只是同文档多视图；如成立，可讨论同身份同内容只返回一份正文。不要用此机会规定讨论对象、丢掉不同稿或隐藏其他可见文件。[原生可见代码](../../../src/vs/platform/beacon/common/beaconPages.ts)当前逐source返回，没有内容去重。
3. **让产品事实更容易被按需找到。** `.bcnb`和`.cph`都已有真实入口及产品知识。本轮真正的问题是模型未按需取用就宣称缺能力。可用评测检查主题目录／工具边界是否足够自然，而非再增加Notebook读取或CPH配置工具。
4. **保留latest，衡量不使用时的实际成本。** 本轮15次run调用只用1次latest；明确“最新”问题通常仍走文件目录→ID。无错误不等于最短路径，但这是一次有限观察，不能立刻强制先latest，也不恢复动态include／复杂参数。可在同场景固定对照中评估参数说明是否清楚区分目录与详情。
5. **回答中的事实强度和篇幅。** 数据选对后仍会加“无stderr”“启动开销”“算法定案”等超证据陈述，并搬出记录ID、hash与时间。优先加入真实性与克制的评测材料；提示若调整，维持少量共性原则，不按每句错误追加禁令。
6. **保留已经有效的设计。** 自足run、完整稿hash、Notebook统一位置、真实失败入队和明确截断，本轮都直接帮助继续工作；不要因访谈再引入快照库、pending存储、永久结果库或功能页结果旁路。

以上均未实施。I01的需求应保留，工程归因和实现方式仍交负责人把关；也不因I09的问题要求改变已确认的stdout/stderr显示方式。

## 5. 教学和访谈输出中仍暴露的问题

- **输出流串层**：W05、W06、W07及后续复述把Runner/Notebook写成无stderr；I09明确更正。CPH运行stderr为空则有真实字段支持。
- **计时归因过强**：W05、W06、I06以小输入耗时直接断言启动开销；记录只有elapsed，不拆进程启动与计算。327ms也不天然“更接近真实CPU时间”。
- **边界证明被扩写**：W08R把n=1用例的重复查询`0 0`也说成验证重复元素；它验证重复查询与单元素边界，并没有验证多个相等数组元素。
- **访谈转教学并引入错误**：I08说“算法可以定案”，又给ans=-1的边界模板，并直接用“第一个>x的位置减第一个>=x的位置”求次数。对`[1,3,3]`查询3，模板前者为-1、后者为2，得到-3而非2；必须先统一不存在边界为n+1等一致哨兵。这段是访谈中新生成的教学，不是工具缺信息。
- **自述的绝对化和因果编造**：“每次重读”“每次两份代码”“记录只是晚到”“并行零代价”等都强于现场。I06把“建议补测”回忆成已经实际采用；I08试图自查时仍把三组测试当作更大范围正确性证明。未每轮重读也不等于违规，已有材料充分时可以直接解释。
- **短答仍偏长**：W05要求简要，依然多层小节、ID和完整复盘；W08R也扩展新测试建议。访谈本身允许展开，其篇幅不能直接与教学短答混算。
- **不同规则应避免因果歧义**：4096字段截断与32KB元素拒收是两条独立规则。W09并列两者后称“这就是……截断的原因”，指代含混，尚不足以认定它明确声称本记录触发32KB拒收；后续说明应写清。现场11,160字节记录已入队，没有触发32KB拒收。
