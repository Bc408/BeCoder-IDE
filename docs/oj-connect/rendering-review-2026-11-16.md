# OJ Connect / Beacon 渲染调查与统一方案

日期：2026-11-16。实施依据为[内容渲染性能优化、能力统一与去冗余设计](../superpowers/specs/2026-11-16-content-rendering-optimization-design.md)。固定默认 One Monokai，不引入主题同步；本文分别记录源码、生产页面测量和桌面验收边界。

## 追加审查与流式 p95 修正（2026-11-16）

负责人确认上一版 OJ Connect 代码高亮视觉已过关。本轮保护该效果，审查 OJ 流程及共享／Beacon 渲染，处理可证实的冗余和缺陷。开始修改前，按负责人要求以 `df2807f3` 保存原样本地快照；仓库 pre-commit 报告 191 项 hygiene 问题，本次跳过 hook 经负责人明确同意，失败日志保留，未推送。后续修正尚未再次提交。

### 审查结论与实际修改

- **已修正 P2：复制失败无提示。** 样例／编译输出旧自定义元素在 clipboard 拒绝后静默返回，题面却显示失败提示。现在薄 React 容器调用同一 `installCodeCopyButtons`，删除每块额外 React root、自定义元素、重复图标及对应 CSS；空白与末尾换行仍由 code 原文复制。新增拒绝／成功重试回归先 RED 后 GREEN。
- **清除死通路。** `CommandBrowserHost` 只实现现行 `AtCoderHost`，删除无扩展生产调用的 `submit/revealResult` facade。核心实验入口、真实提交协议、验证码规则及账号未动。
- **去除高亮重复工作。** `patch()` 统一拆行、扫描稳定前缀及尺寸预算；Worker 不再单独拆行预检，full-view `update()` 调用同一算法，不再让 patch 路径先复制全部 token 行再截后缀。预算新增确定性 RED→GREEN；继续状态与超时规则保留。
- **删除未消费 HAST 参数。** Beacon 自定义组件不使用 node，移除 `passNode` 和对应参数。
- **保留有作用的边界。** 纯解析器、Worker、DOM 展示、消费者业务容器；提交控制器、平台协议、跨进程响应校验、缓存去重及 SourceBinding 各有真实职责，不因去冗余重新揉合。Toolkit 未消费控件已由 tree shaking 移除，不扩展为无关整理。

独立只读审查与主审未发现可证实的重复交题、认证失败无限重发或共享渲染阻塞缺陷；这不等于真实站点全面验收。未引入新认证、主题同步、增量 Markdown 框架、额外缓存服务或第二套引擎。

### 根因与最小修正

生产 bundle 临时埋点显示 2000 行样本的全文解析中位约 7.8ms，JSX 转换接近 0ms。Chromium trace 显示主要成本来自数千行共处同一 inline formatting context：新增尾行使稳定前缀也参与布局。固定 16ms 等待存在额外延迟，但单独 rAF 调度试验未改善，已撤回；产品仍保留既有合并计时。

Beacon 的 `.code-line` 现用 `inline-block` 隔离每行的内部排版，`min-height: 1lh` 保留空行，`max-width: 100%` 保留换行。临时 trace 单轮 Layout 总耗时约 2631→686ms；此 trace 仅用于定位，不作为最终五轮数值。初版缺少 min-height 导致空行高度从 84px 降到 46px，被新增回归抓住，修正后通过。真实原文、Tab、空行、缩短、追加、语言替换、资源失败及包裹长标识符均核对；已查看自动换行截图。OJ 静态代码 CSS 不受此布局修改影响。

## 结论与边界

可以统一内容渲染核心。两边已经使用 unified / remark / rehype，主要 UI 都使用 React；不存在必须维护两套完整 Markdown 管线的技术栈障碍。建议复用解析、AST 转换、内容清洗、数学和代码节点、内容组件，以少量明确策略保留洛谷方言、Beacon 流式与图片限制。OJ 的题目头部、样例／CPH／提交和 Beacon 的会话／滚动／动画仍由各自容器拥有。

不建议原样复制 Beacon Worker，或立即选定某套高亮引擎。先削减重复解析和全量更新，再按覆盖范围、冷启动、长代码与流式实测选择。共享源码不等于跨 Webview 共用 Worker，也不需要建立新的跨进程全局渲染服务。

## 实施前基线与确定问题

### OJ Connect

- `src/markdown.ts`：洛谷 Markdown → 上游 `@luogu-saver-next/markdown-renderer@1.0.3`（Shiki / KaTeX）→ HAST → 自定义转换 → HTML；此前另用 remark / parse5 清空作者 style。源码中的“without parsing Markdown here”注释已不能准确描述整个路径，后续实施时应一并校正。
- `webview/content.ts`：网站 HTML → DOMPurify → KaTeX / highlight.js；未由 Shiki 处理的洛谷 fence 也走 hljs 补充。Shiki 的 GitHub 与 hljs 的 Tomorrow 配色不同，语言范围也不同。
- 实际语言探测：Haskell、OCaml、Julia、Pascal 均未被预载 Shiki 的15种语言及 hljs/common 覆盖；C#/Kotlin/Lua 走 hljs，C++/Python 走 Shiki。缺主题文件不是根因，构建已引入 hljs 主题。
- 既有 `MarkdownService` 已有32项／8 MiB缓存及并发去重。热命中极快；继续堆一层缓存不能解决首次打开。
- 相比上游，额外的全 Markdown 安全预解析、输出 HTML 再解析／遍历／序列化增加成本；当前 walker 还进入所有高亮 token。保留安全边界是要求，具体遍历是否必要需要用等价安全回归证明后才能删。
- 面板状态包含完整正文，但 Content 的 effect 已按内容串去重，不能误称每次选语言都重做高亮。
- `pre` 与 `code` 均有滚动容器。截图中的小箭头在 DPR1/1.25/1.5/2、12–16px本地几何测试未复现，根因仍未证实。

### Beacon

- `webview/elements.tsx`：平滑输出每帧改变传给 ReactMarkdown 的全文，重复数学预处理及 Markdown 解析。
- `useCodeSyntax.ts` / `syntax.ts`：Worker 内部有增量着色，但通信仍发完整代码、回完整 token；`CodeBlock.tsx` 再映射全文 token spans。
- 允许保留旧前缀高亮快照，但展示没有补齐新增纯文本尾部，Worker 落后会推迟代码可见增长。
- Worker 将253种 Shiki grammar资源和内置扩展语法打包；当前产物9,118,314字节（8.70 MiB），另有466,610字节 WASM。Beacon 使用 TextMate/Oniguruma着色，Shiki在此仅提供grammar资产。
- 当前主题固定取构建时 One Monokai；并非跟随当前编辑器 token theme。主题统一和深浅色／高对比验收需要一并考虑。
- 最后一个代码块卸载即销毁 Worker，有再次冷启动的可能；本轮未测真实重挂载频率，不将其表述为已复现卡顿。

## 建议的统一管线

```text
Markdown ── 基础解析＋少量方言转换 ──┐
                                    ├─ 共同AST/HAST → 作者内容清洗
网站HTML ── HTML解析／站点内容适配 ──┘
    → 代码／数学语义节点 → 共同内容组件 → OJ题面／Beacon消息容器
```

优先评估放入已有 `extensions/becoder.shared` 的内容渲染模块，共享源码与构建资产。保留两个业务容器，不互相导入另一扩展，不引入庞大的插件注册框架。React18（OJ）与19（Beacon）目前不同，共享组件需要各自构建／类型验证，不要求强制升级或共享运行时实例。

共同核心可包含：基础Markdown/GFM、数学语义与KaTeX、作者内容清洗机制、URL校验、语言别名／grammar／主题、高亮、代码块／复制、静态内容缓存。作者内容先清洗，再生成可信数学／高亮样式，目标是消除当前重复整文解析，同时保持作者style不能覆盖产品UI。缓存键包括方言、策略与影响输出的主题版本；不再加重复缓存。

差异作为明确适配保留：

| 输入／消费者 | 需保留的行为 |
| --- | --- |
| 洛谷 | directives、callout、合并表格、题面图片、受限raw HTML、相对网址、嵌入转链接 |
| Beacon | 换行规则、禁用图片等当前内容政策、不完整数学暂态与停止／完成语义 |
| AtCoder原生HTML | 直接进入共同HAST，保留题面／数学／样例语义，不转回Markdown |

统一内容清洗实现不等于统一权限；洛谷的raw HTML／图片不能自动开放给Beacon。上游渲染器现有公开接口只返回HTML，没有AST／代码节点钩子；需评估带来源声明的最小源码提取或对应源码改造，不能继续叠一轮HTML解析来假装统一。

## 性能优化与迁移顺序

1. 固定代表性内容与当前截图：多语言、洛谷表格／指令、多行公式、未知语言、长单行、1/10个代码块、100/1000/3000行、深浅主题、精确复制。分别计时解析、高亮、传输、DOM提交及绘制，补上真实Webview测量。
2. 以同一基础解析／HAST管线接入 OJ静态题面和Beacon已完成消息；复用上游已验证的方言与数学处理，合并重复预处理和输出往返。保持样例原文，不把源码复制绑定到着色DOM。
3. 迁入共同数学／代码内容组件。对 TextMate、Shiki 等候选比较覆盖、主题与性能，再保留一条主路径。grammar按需加载、未知语言立即纯文本展示；避免每个代码块挂Monaco，避免长期保留多套fallback链。
4. Beacon流式使用同一内容内核，但解析与逐帧视觉输出分开：新数据合并调度，动画只控制已解析节点；稳定子树／代码行复用，新增代码先显示原文再补色，Worker只传变化行。先做调度和复用，不立即自研完整增量Markdown解析器。
5. 进一步尾部增量只在明确失效边界下实施。不能按空行简单切块，列表、表格、引用定义、HTML、fence可能跨块。消息完成后以同一静态内核校准结果；性能／行为等价后删除旧路径。

这是建议路线而非性能承诺。验收应比较冷开／热开、语言切换、长代码与流式响应、复制空白、主题、窄侧栏、公式和恶意内容；共享后的路径必须实际更简洁且指标改善，不能只减少依赖名而增加转换层。
