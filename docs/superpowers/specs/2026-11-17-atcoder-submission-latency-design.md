# AtCoder 提交耗时优化与链路简化设计

日期：2026-11-17。状态：负责人已批准整稿及修改、实现、测试、干净 stage 交付；实施见[任务计划](../plans/2026-11-17-atcoder-submission-latency.md)。源码候选已经收敛为单一路线，最终构建与负责人验收分别记录；研究探针的成功不代表本设计已经交付。

## 1. 目的与适用范围

缩短 OJ Connect 从源码编辑器按 Ctrl+Alt+S 到打开本次评测记录的等待，减少不必要的网页编辑器操作、页面导航和重复请求。结果页尽量沿用 vscode-luogu 4.20.0 的布局、控件及反馈，允许 AtCoder 数据和协议保留差异。

优先级为正确受理与防重、减少等待和链路复杂度、结果排版接近洛谷。负责人明确选择按需准备，不以后台预热换取较短的按键后计时。

依据：[产品方向](../../../VISION.md)、[OJ Connect 产品要求](../../oj-connect/README.md)、[当前架构](../../oj-connect/architecture.md)、[此前体验设计](2026-11-16-atcoder-experience-design.md)，以及本轮采证与源码调研。洛谷参考固定为 v4.20.0 / `987ca974b5419230a07b59a195ec44026e16f6f4`。

本文在提交传输、准备时机和任务页面生命周期上取代此前设计中的对应路线；语言偏好、题目标识、CPH、共享会话、源码保护及统一界面要求继续有效。历史计划中的原生 Submit 属于当时基线，不与本设计并行作为未来备用发送路线。

## 2. 当前事实与证据边界

文档编写前分支 `OJ_connect`，HEAD `ba0d14cc6ead7ae9d4e0d8ad61ee4b7b9b73e4d3`，存在 50 个既有 dirty paths，涉及 OJ、Beacon 与宿主等所有者；本轮不整理或覆盖这些变更。

| 环节 | 当前源码／已有采证 | 本轮目标 |
| --- | --- | --- |
| 页面取得 | `browserOjConnectFeature.ts` 的 taskOwned 路径新建隐藏题目页，并等待当前页面就绪 | 用户发起提交后，直接准备本次官方提交页 |
| 源码准备 | `atcoderWorkflow.ts` 通过文件上传入口、change 事件及 textarea 同步填码 | 源码直接进入完整表单请求，不以 Ace 或上传控件状态作为发送条件 |
| 实际发送 | `atcoderShortcut.ts` 原生 requestSubmit，事务观察导航及发送标记 | 固定页面内 fetch，一次逻辑任务只走这一条发送路径 |
| 回执确认 | 等原生返回本人列表，再请求列表和源码详情核对 | 复用 POST 最终返回的列表，保留唯一新记录和源码核对 |
| 初始结果 | 记录读取和发送事务仍依赖已有承载页及其映射 | 确认时已有的数据用于初始结果；后续只读查询不持有提交页面 |
| 结果更新 | 当前 AtCoder 读取完成后通常间隔两秒 | 优先采用官网状态响应的 Interval；缺失或无效时沿用现有合理间隔，不累积并发查询 |

已完成的有限实验：

- 正式注册的隐藏视图中，四次同源完整表单 fetch 均产生唯一新记录，核对源码并最终 AC；发送至源码核对为 0.588～0.919 秒。
- 上述计时不含最初 openTask 加载题目页；四次仍经过旧文件填码辅助函数，尚未证明完全移除 Ace／上传依赖后的本项目真实提交。
- 另有九次只加载实验，八次验证就绪、一轮普通 Edge 因资源连接关闭未就绪，全部零次交题。正常 stage 样本验证需 5.450～8.202 秒；CPU 减速时为 15.052 秒，恢复后为 7.373 秒。
- 这些证据说明浏览器本地验证执行与网络传输均有成本，不支持把全部数秒归为固定服务端等待；也不证明可以消除网站验证或保证冷启动低于一秒。
- 普通 Edge 也出现秒级等待和资源失败，不能把更换浏览器／HTTP 库当成已有证据支持的根治办法。

原始脱敏证据在本地 `tmp/oj-connect-audit/evidence-atcoder-20261116/`；替代路线报告在 `tmp/oj-connect-audit/alternatives-atcoder-20261117/`。它们是本机研究材料，不能作为其他开发者必须具备的依赖；关键结论与公开固定来源已归入本文。

## 3. 已确认的架构决定

1. **按需准备。** Ctrl+Alt+S 或题面明确提交动作才启动本次准备。扩展激活、打开源码、看题、Import 均不预热提交环境。
2. **任务页面短生命周期。** 每次提交拥有自己的官网提交页，与普通持久浏览器共用会话，不改写用户正在浏览的页面或其草稿。本任务成功、未发送失败或受理不明后均释放任务页面及监听；不跨提交复用，不建立页面池。
3. **单一发送路线。** 正常官网验证就绪后，在页面内以完整原生表单字段发起一次同源请求。移除原生按钮／requestSubmit 备用发送链路，不保留“先直接 POST 试错、失败再走网页”的双路径。
4. **后台完成。** 普通准备、提交、核对和评测不自动显现内置浏览器。未登录或需人工认证时在插件内明确提示，由用户主动使用既有入口；不在本轮引入新认证形式。
5. **参考洛谷的业务节奏。** 正在提交 → 取得本次正式回执 → 打开结果页 → 持续更新。AtCoder 取得正式 ID 所必需的核对保留；结果展示失败不撤销已确认回执、不重发源码。
6. **控制复杂度。** 修改已有站点适配、宿主事务和共同界面的小接口；不引入新的通用传输框架、账号库、提交队列、认证服务、持久题目绑定库或常驻预热管理器。

## 4. 目标使用过程与数据流

1. 按键时立即固定当前编辑器源码、版本、题目与文件来源，包括未保存内容；之后继续编辑不改变本次源码。插件立即显示准备进度，编辑器仍可操作。
2. 按既有目录／文件名规则确定题目，沿用主动选择的 C／C++ 编译器偏好；本次官网可用目录不含该选项时重新选择，不自行替换版本。
3. 宿主在当前窗口及当前持久会话内建立正式注册的隐藏提交页，直接导航官方 `/contests/{contest}/submit?taskScreenName={task}`；不先加载题面，也不另开独立账号会话。
4. 读取真实表单及当前题目语言目录，正常等待网站验证。只等待发送所需的表单、站点初始化与验证条件，不把整页所有无关资源完成作为固定前置。存在与否须以正常初始化后的真实结构判断，不能因早期字段尚未挂载就认定免验证。
5. 在发送前完成必要的本人记录基线读取。与准备阶段可独立进行的只读请求并行，不为提交额外串行刷新侧栏登录摘要；明确登录失效由实际响应判定。
6. 验证本次任务仍有效、目标、语言及源码符合约束。由完整原生表单构造数据，明确设置题目、语言和源码；保留原站当前隐藏字段与正常验证响应，在页面内 URLSearchParams 编码并 fetch 一次，POST 目标固定为 `https://atcoder.jp/contests/{contest}/submit`，不能由任意 form.action 决定。凭据和验证响应不跨给扩展、不落盘。
7. 使用 POST 跟随正常重定向后的响应核对本人列表；最终响应须为相同 origin、相同 contest 的 `/submissions/me`。目标不符时不能仅解析正文认定成功，应按受理不明只读确认。识别基线之后唯一匹配题目、语言及账号的候选，再读取候选详情核对源码；没有唯一候选或源码不一致时不能宣布成功。
8. 确认正式 ID 后立即交付共同结果页，不等待最终判定或官网记录页导航。确认过程中已取得的详情用于初始记录展示，避免紧接着为相同初始数据再次请求详情。
9. 回执交付、发送占用和任务页释放不以面板加载完成为条件；后续按正式 ID、记录所属会话范围进行只读状态与详情请求，等待评测不占用提交通道，也不依赖提交页面存活。

第一轮与后续显式提交均走相同按需流程。连续按快捷键时按已有忙状态立即反馈，不排队、不记录待会自动发送的源码。

## 5. 正确性、失败与资源所有权

HTTP 200、重定向到包含 submissions 的 URL、以及列表第一行，均不能单独代表本次解答已受理。正式回执必须对应本次源码和目标题目；已有的唯一 ID、语言与源码保护继续保留。

| 状态 | 用户反馈与允许动作 |
| --- | --- |
| 明确尚未发送，准备／语言选择失败 | 结束本次任务并说明原因；后续可由用户重新发起 |
| 官网验证未能在有界等待内就绪 | 明确未发送，提示可主动到内置浏览器手动提交／认证；不自动打开网页或切换发送协议 |
| POST 已发出或无法排除已发出，回执无法核对 | 显示受理不明，仅允许只读查询确认；不自动重发、不回退按钮发送 |
| 已取得正式 ID，面板／后续读取失败 | 保留正式记录链接和最后结果，提供查询重试；不回到提交阶段 |
| 页面／窗口关闭、会话失效或扩展停用 | 停止本任务后续动作，清理请求、页面和监听；迟到脚本或验证不能再次发送 |

保留现有任务取消与发送前有效性复查，复用已有有界等待和请求中断能力，不新增逐层重试窗口。发送后的“停止本地等待”不称为撤回提交；不增加误导性的取消提交按钮。

结束时必须证明任务页不再可能晚发，才允许释放发送占用。受理不明的只读确认保留必要题目、语言、源码校验和会话范围信息，使用已有临时尝试记录；不为确认长期保留网页，也不新建持久任务数据库。

已确认记录的读取和发送页释放分开。释放的是本任务拥有的资源，不关闭用户标签，不清理登录数据，不影响其他 OJ。

## 6. 实施所有者与去冗余范围

| 所有者 | 目标职责 |
| --- | --- |
| OJ Connect `workflowController.ts` | 源码快照、语言选择、已有并发约束、进度、正式记录打开；不持有凭据或网页对象 |
| AtCoder adapter／固定 site-scripts | 站点题目与语言解释、官方表单结构、固定页面内发送操作、原生状态解释 |
| `browserOjConnectFeature.ts`／`atcoderBridge.ts` | 当前窗口、任务身份、持久会话范围和任务页面生命周期，固定受限调用 |
| `atcoderTransaction.ts`／浏览器宿主 | 正常验证、不可逆发送边界、一次请求、回执与源码核对、取消和资源释放 |
| 记录读取／`recordController.ts` | 绑定正式 ID 的只读状态更新、官网 Interval、必要详情、关闭和重试清理 |
| 共用 record Webview | 洛谷式排版、真实数据、动画和复制；不另建 AtCoder 页面或渲染器 |

替换时沿消费者删除旧路径：原生 requestSubmit 与专用标记／导航等待、文件上传填码与 Ace 同步、任务先开题目页的前置、重复列表／初始详情读取，以及仅服务旧发送链路的测试与映射。

必须先区分真实消费者：实验读取命令、题目 Import、普通浏览器、CPH 和用户草稿保护不因名字相似被连带删除。只在实际新路径取代旧路径后移除对应实现，不保留两套生产发送策略，也不删除仍承担防重或生命周期职责的保护。

初始详情与结果页通过窄结构化数据交接；优先复用现有数据类型，必要时仅增加实际字段，不另建通用缓存／事件总线。结果状态可共享表达，站点网络协议仍各自拥有。

## 7. 结果页面与洛谷对齐

负责人提供的视频 `D:/_Obs/2026-11-16 21-31-28.mp4` 是外观参考，本轮已抽帧核对，未用于推算 AtCoder 耗时。参考效果为右侧记录详情、紧凑标签／值信息行、清晰状态、测试点卡片和后续编译信息。

- 使用已有洛谷 record 组件与样式，保持当前认可的代码高亮、复制控件和固定配色，不改共享实时渲染管线。
- 按正式 ID → 题目 → 状态 → 可得元信息 → 原站测试信息 → 编译信息安排内容；没有来源的字段省略，不为填满版面补造分数、满分、分组或用量。
- 初次等待与评测中使用现有洛谷蓝色转圈／卡片动画，终态停止；更新失败停止有效跟踪动画，保留最后状态并提供只读重试。
- 仅有 WJ 时显示总体等待，不猜数量。原站仅提供 x/y 进度时保留其语义；已有按真实总数展示的等待点位不能冒充已取得的各点判定，不为视觉对齐增加虚假测试点数据。
- AC、WA、CE 等保留原站标识；CE 展示实际可读编译输出。记录初始状态先可见，后续详情按需补齐，不等待终态才绘制整个面板。
- 优先保证窄分栏可读、元信息不重复、卡片正常换行。视觉调整限提交／评测区域，不扩大到题面翻译、题库、侧栏或其他 OJ。

洛谷布局对齐不是逐字段复刻；没有真实信息的区块留空或跳过。视觉验收与提交协议、性能验收分别记录。

## 8. 耗时定义与优化验收

每次以同一任务标识记录以下脱敏时间点，不记录账号标识、Cookie、CSRF、验证响应和提交正文：

| 时段 | 定义与目的 |
| --- | --- |
| 按键到本地进度 | 确认命令立即接收，避免用户重复按键 |
| 页面准备 | 视图创建、文档／表单就绪分别记录，不笼统称为验证时间 |
| 官网验证 | 正常验证开始／就绪或失败，独立于本地准备与网络发送 |
| POST 到正式回执核对 | 一次请求、回执解析和必要源码读取的实际时间 |
| 回执到结果面板首绘 | 验证 UI／清理不再阻塞正式记录呈现 |
| 状态取得到 UI 更新 | 检查序列化、重复渲染及动画是否带来额外延迟 |

本方案没有预热，必须报告真实按键到结果页首绘，并保留完整总耗时；不能只报不足一秒的发送阶段。人工语言选择等待、网络／验证失败和网站判题排队分别列出，不从失败样本中挑选好看的时延。

验收以当前基线的相同题目、语言、账号、机器及相近网络条件作比较，区分资源冷／暖缓存；不将两个不同站点的单次录像当作速度对照。小样本只给样本值、范围和中位数，不宣称 p95、长期可靠率或固定毫秒 SLA。

结构性目标必须达成：无初始题目页导航；无上传／Ace 同步等待；无原生提交后导航等待；回执列表和初始详情不存在可避免的重复读取；无自动重发；正常全程不显现网页。真实总时延是否改善另由运行数据证明，不能以源码行数减少代替。

## 9. 验证与交付顺序

1. 先用独立短探针验证直接设置 sourceCode、不操作网页编辑器的真实正常提交；沿用既有测试授权与明确练习题，不为吞吐压力测试反复交题。逐次记录唯一 ID、源码一致和最终结果。
2. 实现一条按需生产路径，先验证发送前停止、页面销毁、验证码晚到、回包丢失、受理不明只查询和重复按键；实际发送次数必须可核对。
3. 结果读取脱离任务页，回归初始 WJ、进度更新、AC、已有 CE 详情、失败重试、关闭／重开、换题及会话失效。CE 优先只读已有记录，不另交错误代码。
4. 记录完整快捷键耗时和面板首绘，至少覆盖首次提交、相同题再次显式提交、另一道题和应用重启。多次成功不是长期可靠率证明，失败保留，不算作通过。
5. 复核已无消费者的旧路径并删除，运行相关合成／集成回归；保护洛谷提交、图片验证码既有收尾、结果推送和共享渲染能力。
6. 按实施计划预检真实存在的验证入口，依次完成聚焦检查、client 类型检查、OI 扩展编译及 Windows stage 构建；渲染截图与真实网站验收单列。

用户已允许使用隔离 BeCoder／浏览器和已有登录信息，以及 `D:/c++` 下可 AC 解答作测试；不使用 computer use，不把普通开发账号交题变成批量提交。采证仍不打印认证信息，临时调试环境结束后收尾。

负责人后续已批准按任务计划实施、测试与干净 stage 构建，不迁入旧数据。本文不预报最终检查通过、总耗时已改善或新 stage 已完成；Git 提交／推送、Setup 及其他站点接入不在本轮范围。
