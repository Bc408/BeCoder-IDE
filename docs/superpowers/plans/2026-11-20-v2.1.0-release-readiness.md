## 2. 全局保护条件

- 保留源码、未保存稿、用户模板、样例空白和尾换行；显示归一化不得污染原题 DTO、CPH 数据或实际提交内容。
- 保留五站独立协议和现有题型范围，不因同域名扩大到赛事、考试、Gym、交互题或权益受限题。
- 不引入提交等待队列、自动重放、备用发送路线。受理不明只读核对；蓝桥 source/report 各最多一次，取消后不能补发尚未发送的 report。
- 账号凭据仍由真实浏览器 Session 持有；不复制 profile、导出 Cookie，不降低证书、TLS、代理、sandbox、工作区信任或权限保护。
- 题面标题和普通题目链接保持内置打开；外部浏览器仅由明确标示外部去向的用户动作授权，不能在登录失败、错误恢复或普通导航时隐式启动。
- 提交语言继续分站、分 C/C++ 保存；四站沿 C++20/C17 向上择优并考虑 GNU/GCC、O2、MSYS2 等已证实能力；蓝桥保留已批准 C++17/官网唯一 C 选项例外，不伪称网站支持未提供的标准或开关。
- 洛谷为共同视觉标杆，不复制其他站缺失的业务数据。缺失值省略、真实零值保留、未知判词保留；不伪造分数、资源、点数、逐点完成过程或成功状态。
- 保留现有工具链、依赖、缓存、构建物与个人数据；不以清缓存、重装依赖、删除目录作为常规检查步骤。生成文件只由拥有者构建写入。
- 每项证据标明源码/自动测试/合成原生/实际渲染/官网/负责人验收层级；不把其中一层当作其他层的证明。

### 9.3 发布授权边界

此处只规划发布所需证据。当前推送 `OJ_connect` 不是发布正式 2.1.0。后续须明确所选发布路径：

- 本地已验证 Setup 发布：获得 `main` 与 Release 发布授权后，使用该确切本地候选；不因此触发云端重建。
- 云端发布：须同时明确授权接受改动进入 `main`、发布 Release、在干净云 Windows runner 重建并验证。仅按手动 workflow 派发，稳定标签为 `v2.1.0`；不新增 push/tag 自动触发。
- 正式发布时再完成用户向 release notes、标签、Setup 上传及远端校验。不得提前承诺“已发布”或以分支推送代替发行物验收。

## 10. 收敛条件

- [ ] 当前五站正常旅程、共同边界及浏览器/主页矩阵逐项有证据，未跑/失败/不适用各自说明；无悬而未决的 P0/P1。
- [ ] license、原版权/NOTICE、资产来源、实际随包依赖及对应源码记录闭合；组件清单、语言包摘要、verifier 与真实产物一致。
- [ ] 核心一次发送、回执身份、取消/会话、源码/样例保护及外部浏览器明确授权均未退化；清理只移除经证实的冗余。
- [ ] 文案和当前文档一致；性能有当前基线、对照及剩余成本，优化不以正确性换数字。
- [ ] 独立只读 review 和主代理最终复核完成，最后必需检查均针对最终输入；失败尝试、修复与重跑可追溯。
- [ ] 若进入完整发行候选阶段，同一源码的 stage、直接包验证、Setup 及直接 Setup 验证通过，负责人运行验收单独确认；否则明确停在“源码/候选 stage 就绪”，不能写“可正式发布”。

**执行方式：** 主代理按 A→F 顺序推进和修复，独立 agent 只读审查许可、站点事务、浏览器/主页三个边界，完成后统一复核；内部逐项验证，收敛后再交付候选，避免反复打包占用负责人验收时间。实施按负责人后续明确授权推进；每项完成以执行报告及对应台账为准。
