我会同时查看题目和你当前的代码。## 结论先说

你的代码**逻辑上是对的**（样例能过），但按满分数据范围会 **TLE**——所以接下来最值得验证的不是“答案对不对”，而是“最坏情况下跑多快”。

## 对照题意的两点

1. **读入与区间下标一致**：题目保证 `1 ≤ l_i ≤ r_i ≤ n`，你 `a[1..n]`、循环 `for (i=l; i<=r; ++i)` 都对得上，`a[100005]` 也够放 `n=1e5`。这部分没问题。
2. **单次询问是 O(r−l+1)**：每次询问都从头把区间加一遍。

关键在数据范围：

| 数据 | 规模 |
|---|---|
| 50% | n, m ≤ 1000 → 暴力最多 1e6 次加法，稳过 |
| 100% | n, m ≤ 1e5 → 最坏 m 次都是 `[1, n]`，共 **1e10 次加法** |

1e10 次加法在 1s 限时下远远不够（大致只能承受 1e8~1e9 量级）。这正是这道题作为“前缀和入门例题”的意义：**查询次数多了，就不能每次重新累加**。

顺带一个次要隐患：`answer` 用 `int`。本题 `a_i ≤ 1e4`、`n ≤ 1e5`，整段和最大 1e9，还在 `int` 范围（约 2.1e9）内，**这一题不会溢出**；但如果以后 `a_i` 变成 1e9 或 `n` 更大，就要换 `long long`。养成用 `long long` 存和的习惯成本很低。

## 最值得做的验证

1. 造一个最大档数据（`n = m = 1e5`，全部询问 `1 n`），本地计时跑一遍，亲眼看到约 1e10 次加法的耗时——这比“感觉会超时”更有说服力。
2. 换前缀和后，用同一份数据再计时，对比差距。

## 改法：前缀和

预处理一次 `s[i] = a[1] + ... + a[i]`，之后每个区间 `[l, r]` 的答案就是 `s[r] - s[l-1]`，单次 O(1)。

```cpp
#include <bits/stdc++.h>
using namespace std;

long long s[100005];   // s[0] = 0，天然处理 l = 1 的情况

int main() {
    ios::sync_with_stdio(false);
    cin.tie(nullptr);
    int n;
    if (!(cin >> n)) return 0;
    for (int i = 1; i <= n; ++i) {
        long long x;
        cin >> x;
        s[i] = s[i - 1] + x;
    }
    int m;
    cin >> m;
    while (m--) {
        int l, r;
        cin >> l >> r;
        cout << s[r] - s[l - 1] << '\n';
    }
    return 0;
}
```

两个容易踩的点：

- **`s[0] = 0`**：当 `l = 1` 时用到 `s[0]`，全局数组默认就是 0，所以不写也行，但心里要清楚这是靠什么成立的。
- **`s[r] - s[l-1]`，不是 `s[r] - s[l]`**：`s[l-1]` 才是不包含 `a[l]` 的那部分。用样例验一下：`s = {0,4,7,9,10}`，`[2,3]` → `s[3]-s[1] = 9-4 = 5` ✓。

改完后再跑第 1 步那份最大数据，应该是毫秒级。要不要我帮你把这份对拍/计时的小测试也搭一下？

## 逐点核对

`s` 是全局数组，零初始化，所以 `s[0] = 0` 成立——这正是 `l == 1` 时 `s[l-1]` 依赖的东西。`n ≤ 1e5`，最大下标 1e5，数组开到 100005 够用。用 `long long` 后整段和上界 1e9 也不再是问题（虽然本题 `int` 也够）。

```cpp

```

`l-1` 是对的，`l=1` 时取 `s[0]=0`。没有 `if (l==1)` 之类的特判分支，也不需要。

## 值得一起讨论的取舍

**① 自动成组，还是用户显式创建？**
按 `filePath` / 题号自动推断分组几乎零成本，但同题多次尝试会被错误合并（比如你的暴力版和前缀和版，本来是一个连续的探索过程，也可能被当成两次独立提交）。显式创建可靠但增加仪式感。我倾向**自动推断 + 允许命名和固定**。

**② 记录存多久？怎么存才不贵？**
永久保留每条含完整源码的记录成本高。折中方案：每条只存**哈希**，只对"里程碑"（首次 AC、手动固定）存完整源码快照。这次我就是靠完整快照才敢下结论，所以**哈希不能替代快照**，但可以用来决定哪些值得留快照。

**③ 用例要不要统一？**
CPH 用例和 Notebook 输入块现在是两套。统一会让 Notebook 变重，不统一就会分叉——这次你就不得不把同一组数据在脑子里维护两份。**我倾向统一存储 + 两处都是一样的视图**，但要保证 Notebook 仍然能"就地改一行就重跑"。

**④ 自动生成成果物，会不会把学习本身替掉？**
